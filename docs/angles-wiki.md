# 视角角度、正弦表与“半角”机制（基岩版 1.26.51.01）

在《我的世界》跑酷与移动机制研究中，**“半角（Half Angles）”** 指的是：游戏在计算水平移动方向时，并不是每次都现算高精度的三角函数，而是从一个离散的**正弦查找表**里按整数索引取值；在少数特殊角度下，查出来的 $(\sin\theta,\; \cos\theta)$ 向量的欧氏长度 $\sqrt{\sin^2\theta + \cos^2\theta}$ 会略大于 `1`，从而给水平移动凭空多出一点加速度。

把这套原理迁移到《我的世界》基岩版 **`1.26.51.01`** 后，有两个与 Java 版（含 MCPK Wiki `Angles` 条目）截然不同的核心现象：

1. **正弦表还在，但常规跑跳已不吃半角**：日常地面行走与空中按 WASD 微调已改用标准数学库函数，真正还吃得到正弦表模长放大的，只剩**疾跑起跳、陆地坐骑冲刺、长矛突刺、烟花助推鞘翅、蓄力跳**这 `5` 处机制；激流三叉戟、水下坐骑冲刺与击退虽然也查了表，但随后立刻做了长度归一化，所以没有加速。
2. **理论上存在 `+0.3063%` 的“大半角”，但纯原版玩家转不出去**：无论手动转视角、转视角宏还是 `/tp` 命令，基岩版客户端每刻都会把偏航角强行折回 `[-180°, +180°)`。在纯原版条件下，只有**普通疾跑跳**能用到 `+0.0048%` 的小半角；而长矛突刺与烟花鞘翅不仅在 `[-180°, +180°]` 内没有可用小半角，所有数百万度的大半角也都被这层角度折叠挡在门外。

> **文档分工**：本文面向机制理解与跑酷/玩法对比，尽量略去底层汇编细节；完整的逆向函数地址、十六进制常量与全二进制 `193` 个调用点分布清单请查阅 [`notes/sin-table-12651.md`](notes/sin-table-12651.md)（本文所有机制与数值边界均严格对齐该笔记）。

## 二、半角和“大半角”是怎么凭空多出速度的？

### 1. 正弦查找表怎样工作

为了避免每帧大量调用高开销的三角函数，游戏启动时会先算好一张包含 `65536` 个小数的数组（正弦表，对应整圈 $360^\circ$，每格约 `0.00549°`）。把任意角度 `yaw`（单位：度）送去查表时，程序分三步：

1. **角度换算成“连续格数” `base`**：先转为弧度（`× 0.017453292f`），再乘以格子密度 `10430.378f`（约等于 $\frac{65536}{2\pi}$）。
2. **向零取整得到 `sin` 索引**：把 `base` 直接砍掉小数部分转为整数，取低 16 位（相当于对 `65536` 循环取余），从表里读出 `s`。
3. **加四分之一圈（`+16384.0f`）得到 `cos` 索引**：利用 $\cos\theta = \sin(\theta + 90^\circ)$ 的性质，直接把浮点数 `base` 加上四分之一个表长 `16384.0f`，再砍掉小数取整，读出 `c`。

```text
角度(deg) ──× 0.017453292f──▶ 弧度 ──× 10430.378f──▶ base
                                                      │
          ┌───────────────────────────────────────────┴──────────────────┐
          ▼ (直接截断取整 & 65535)                                          ▼ (先单精度 + 16384.0f 再截断 & 65535)
       sin 索引 i_s                                                    cos 索引 i_c
```

> **建表细节差异**：Java 版是用双精度 `Math.sin` 按精准 $2\pi$ 周期生成的 65536 格表；基岩版在启动时改用单精度 `sinf(i / 10430.378f)` 填充（因为单精度字面量 `10430.378f` 实际值略小于 $\frac{65536}{2\pi}$，填满 65536 项会极其微弱地多越过一点点 $2\pi$）。

### 2. 小半角：正常范围内最多多出 `0.0048%`

按直角三角形性质，同一个角度对应的正弦和余弦必须满足 $\sin^2\theta + \cos^2\theta = 1$。但因为查找表是**按格子截断**的：

- 当角度处于 `0° ~ 360°` 这类普通大小时，先加 `16384.0f` 再截断，得到的 `cos` 索引相对 `sin` 索引通常严格多出 `16384` 格。
- 但由于“向零截断”、负数跨零对称性（或在单精度查表乘除下的微弱边界对齐），有时 `sin` 和 `cos` 在小幅度错位后不再严丝合缝地互相垂直——例如在 `135°` 附近，`|sin|` 和 `|cos|` 同时偏往较大一侧，使合成向量长度 $\sqrt{s^2 + c^2}$ 略高于 `1`。
- 在基岩版的表中，常规范围最佳角度下向量长度约为 **`1.0000480358`**，也就是大约 **`+0.0048%`** 的速度提升，跑酷圈称之为**小半角**。

### 3. 大半角：单精度浮点“丢位进位”带来 `+0.3063%`

**为什么把角度转到几百万度，加速一下子翻了 64 倍？**

关键出在上面框图右分支的那一步加法：`base + 16384.0f`，是用 **32 位单精度浮点数（`float32`）** 完成的。

单精度浮点数的有效数字位数是有限的——数越小时小数很精细；**数变得极大时，相邻两个能表示的浮点数之间的间隔（步长 / ULP）也会跟着变大**：

- 当角度还小（几百几千度）时，加上 `16384.0f` 严丝合缝，一格不多一格不少；
- 当偏航角大到将近 **590 万度**时，`base` 涨到了接近 $2^{30}$（约 `10.737 亿`），此时 `float32` 相邻两个可表示数字之间的间距已经超过 `16384` 的舍入边界！
- 于是，单精度硬件在做 `base + 16384.0f` 时发生向上舍入，算出来的 `cos` 索引不仅加上了 `16384`，还会**额外多偏出去整整 `+64` 个表槽**！

多偏这 `+64` 格相当于把原本成 $90^\circ$ 的两个坐标轴，生生往同一侧掰偏了约 $\frac{64}{65536} \times 360^\circ \approx 0.35^\circ$。当 $\sin$ 和 $\cos$ 数值都接近 $\pm\frac{\sqrt{2}}{2}$、又往彼此倾斜 $0.35^\circ$ 时，合成向量长度直接变为 **`1.0030630315`**，净增 **`+0.306303%`**。

> **负数侧为什么不出大半角？** 在全单精度数值空间穷举后确认：只有让送入查表的 `base` 为接近 $+2^{30}$ 的**正值**时，单精度向偶舍入才会在 `+16384.0f` 这一步多进位 `+1 ~ +64` 格；负数侧 `base` 全区间（$[-2^{31}, -2^{14}]$）都不会产生正向多格偏置，最大模长仅为 `1.0000002270`。

## 三、基岩版里到底哪些机制还能吃半角？

虽然基岩版全程序共存在 `269` 处（`193` 个函数/条目）对 `SIN_TABLE` 的直接引用，但**“查了正弦表”不等于“能吃半角加速”**。经逐项排查静态代码，先排除掉不产生加速的三大类：

1. **普通地面/空中 WASD 移动（已改用标准数学函数）**
   `DefaultMoveSystems`（地面与空中共用核心）已改用 MSVC 运行库函数 `sinf` / `cosf` 旋转按键输入向量，精度足够高，不再查 65536 格表。
2. **查了表但随后按模长单位化（被除回 1.0）**
   - **激流三叉戟发射**（`StartSpinAttackActionSystem`）：先查表拼出三维方向，但紧接着调用硬件平方根 `sqrtss` 算出三维向量真实模长并做除法归一化，再乘等级系数，因此多出来的模长偏差被立刻除掉了。
   - **水下坐骑冲刺**（`DashActionSystem` 水下分支）、**击退与实体推挤**：同理都有 `sqrtss` 归一化。
   - **载具 AI 寻路**：部分载具行为直接走 `sqrtss` + 标准 `sinf` / `cosf`。
3. **一维三角或非推进用途**
   - **游泳俯仰控速**（`SwimControlSystem`）：只查了一维 `sin(pitch)` 决定升降目标速度，不存在正交双轴拼合成模长。
   - **划桨动画、环形渲染、视野判定等**：仅计算动画标量、位标志或渲染点坐标，不给移动矢量乘超额增益。

### 真正吃得到未归一化正弦表加速的 5 处机制

真正把未除归的 `(sin, cos)` 模长偏差直接乘进物理待执行位移（即引擎里的 `mPosDelta`）的机制，按**查表角度公式差异**明确分为 **A 类** 与 **B 类**：

| 类别与公式差异 | 玩法 / 系统 | 触发条件与效果特点 |
| --- | --- | --- |
| **A 类**：直接正向公式<br>`base ∝ +yaw` | **1. 疾跑跳跃水平冲量**<br>（`JumpFromGroundSystem`） | 玩家处于疾跑态并起跳时，仅按**当前面向偏航角**（不看按没按方向键），给水平待执行位移 `mPosDelta.(x, z)` 叠加 **`0.2`** 倍查表向量 |
| **A 类**：直接正向公式<br>`base ∝ +yaw` | **2. 坐骑陆地冲刺**<br>（`DashActionSystem` 陆地分支） | 当 `can_dash_underwater == 0`（如骆驼等陆地冲刺坐骑）时，直接用未归一化的二维查表向量乘冲量写回 `mPosDelta` |
| **A 类**：直接正向公式<br>`base ∝ +yaw` | **3. 蓄力跳水平冲量**<br>（`ApplyJumpModifierSystem`） | 受特殊组件 `PowerJumpFlagComponent` 门控时额外施加 `0.4 × JumpPendingScale` 水平冲量；普通玩家通常不触发 |
| **B 类**：反相偏移公式<br>`base ∝ -π - yaw` | **4. 长矛突刺附魔**<br>（`LungeEnchant`） | 非骑乘、未在水中、未在滑翔，且（非创造等豁免模式下）饥饿值 `> 6.0` 时触发；沿水平面施加 `0.458 × 附魔等级 × cos(pitch)` 的未归一化二维查表冲量 |
| **B 类**：反相偏移公式<br>`base ∝ -π - yaw` | **5. 鞘翅烟花助推支路**<br>（`GlideMoveSystem` 烟花尾段） | 鞘翅常规滑翔时的升力/重力缩放与水平转向重对齐都用了带 `sqrt` 的模长归一化；但**点燃烟花推进的那条加法分支**直接使用了未除以三维模长的查表视线向量（实拍还会叠合 `0.5 × mPosDelta` 混合与 `360°` 插值视线） |

> **补充说明**：此外有一个低速微步分支（水平 `mPosDelta` 平方 `< 0.01` 时以 `0.1` 步进更新）也会读未归一化表；而前表中**玩家疾跑起跳的阻力顺序**经静态 ECS 调度链已证实：起跳那一拍碰撞落地标志直到全拍移动结束才摘除，所以起跳拍本身仍先算地面 WASD 加速并乘地面摩擦（默认 `0.546`），**下一拍**才正式切为空中加速度与空气阻力 `0.91`。

## 四、A 类与 B 类的最佳小半角、大半角数值（为什么长矛用不了 Java 半角？）

因为 **B 类（长矛突刺与烟花鞘翅）的查表公式把偏航角套进了 `-π - yaw_rad`**，相当于把玩家朝向先取反、再额外偏移 `-180°`，这带来了两个极易算错的反直觉结论：

1. **直接抄 A 类 / Java 的大半角，对长矛和烟花完全无效**：
   - 把 `+5898195.0°` 代入 B 类，得到的 `base` 是**负数**（模长仅 `0.9999999`），完全无加速；
   - 简单取反成 `-5898195.0°` 也不行，因为公式里还多减了一个 `-π`（即 `-180°`），模长只有 `1.0000001`；
   - 必须把负角度再多往负方向补足 `180°`，也就是 **`-5898375.0°`**，才能刚好抵消 `-π`，精准命中同一个最优点 `base = 1073733568.0`（槽位 `(57280, 8192)`），拿到完全相同的 **`+0.306303%`** 峰值增益！
2. **正常范围 `[-180°, +180°]` 内，B 类根本没有“小半角”**：
   - 对 B 类在 `[-180°, +180°]` 内做逐点高密度扫描，最大值仅 **`1.0000002270`**（`39.276199°`，相当于十万分之零点零二，几乎是零）。
   - B 类必须越过 `-180°` 边界到达 **`-314.961548°`**，才能获得 **`+0.004804%`**（`1.0000480358`）的 `+1` 档小半角。

| 错位档位（额外多偏槽数） | A 类最佳角度（疾跑跳 / 陆地冲刺） | B 类最佳角度（长矛突刺 / 烟花鞘翅） | 二维向量长度 $\sqrt{s^2+c^2}$ | 速度放大率 |
| --- | --- | --- | --- | --- |
| **`+64` 槽（全局峰值）** | **`5898195.0°`** | **`-5898375.0°`** | **`1.0030630315`** | **`+0.306303%`** |
| `+64` 邻近候选 1 | `5898196.5°` | `-5898376.5°` | `1.0030602304` | `+0.306023%` |
| `+64` 邻近候选 2 | `5898193.5°` | `-5898373.5°` | `1.0030584969` | `+0.305850%` |

## 五、为什么手转视角、转视角宏和 `/tp` 全都用不了大半角？

在 Java 版中，虽然手动鼠标连转几百万度不切实际，但理论上“连续往同一方向转视角”确实会让偏航角一直累加突破 `360°`、从而靠宏慢慢转进 `5898195°`。**但在基岩版里，哪怕用最快的高速转视角宏无限连转，也绝对不可能转出 `±180°` 范围。**

顺着游戏从鼠标输入到服务端同步的整条调用链看下来，原因非常明确：

1. **第一道锁：相机系统本身就不保存多圈角度**
   `CameraDirectLookSystem` 在累加每帧视角转动后，会先用 `fmodf(angle + π, 2π)` 将弧度折叠进 `[-π, +π)`，然后把结果存成**相机四元数**。四元数天然只表示空间朝向，不记录“你转过多少圈”。
2. **第二道锁：每 tick 强制从四元数反解欧拉角并折回 `[-180°, +180°)`**
   玩家旋转更新系统 `TickUpdatePlayerFromCamera` 每一刻都会先从相机四元数用 `atan2f` 算回欧拉角写进玩家旋转组件与头部旋转组件，紧接着在函数末尾对**当前偏航角、当前俯仰角以及上一帧历史偏航/俯仰角**全部执行一遍：
   $$\text{angle} \leftarrow \text{fmodf}(\text{angle} + 180.0\text{f},\; 360.0\text{f}) - 180.0\text{f}$$
   即使命中特殊控制方案分支跳过了四元数重算，控制流依然会汇入末尾这同一段 `fmodf` 折叠代码；载具相机与其他输入视角变换系统也是同样写法。因此每转过 `±180°`，角度都会立刻跳回对侧，根本无法积累。
3. **第三道锁：`/tp` 命令入口同样截断**
   无论是 `/tp ... <yaw> <pitch>` 数值写法，还是 `/tp ... facing ...`，传送命令执行时都会用同样的 `360°` 取余折回偏航角到 `[-180°, +180°)`，并将俯仰角钳制在 `[-89°, +89°]`。
4. **唯一的理论缝隙：网络输入包校验与服务端同步反而不截断**
   与客户端严防死守不同，客户端发向服务端的输入包 `PlayerAuthInputPacket` 在服务端合法性检查里，只检测 `mRot` 是否为合法有限的 `float32`（排除 `NaN` 和无穷大，不限定 `[-180, 180)`）；序列化读取和服务端同步历史角度也直接原样复制 `mRot`。

| 操控方式 | `yaw` 实际可达区间 | 疾跑跳 / 陆地冲刺（A 类） | 长矛突刺 / 烟花鞘翅（B 类） |
