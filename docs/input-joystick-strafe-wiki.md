# 摇杆、斜走与视角灵敏度（基岩版 1.26.51.01 通俗版）

本文面向玩家与跑酷研究者，讲清三件事：**移动输入是怎么合成出来的**、**「三向斜走」到底存不存在**、
以及**键鼠 / 触屏 / 手柄的视角速度公式**。所有数字都来自 `1.26.51.01` 的静态反汇编与逐 tick 实测；
地址、组件哈希与证据等级见证据册 [`notes/input-joystick-strafe-12651.md`](notes/input-joystick-strafe-12651.md)。

---

## 一、移动输入：一条向量，两个来源

游戏每 tick 把「你想往哪走」压成一条二维向量 `mMove`：

- `mMove.y` = 前后（正 = 前）
- `mMove.x` = 左右（正 = **左**）

它有且只有两个来源，**互斥**：

| 来源 | 触发条件 | 结果 |
| --- | --- | --- |
| **模拟向量**（手柄摇杆 / 触屏虚拟摇杆） | 向量的 x 或 y **只要有一个不是 0** | 8 个方向键位**整段不读**，只看模拟向量 |
| **数字方向键**（键盘、触屏 D-pad） | 模拟向量严格等于 `(0, 0)` | 按位相加 8 个方向位 |

也就是说：**模拟输入拥有绝对优先级，永远不会和键盘方向叠加**。

### 1.1 数字方向键的加法和符号

| 键位 | 贡献 `(x, y)` |
| --- | --- |
| 上 `0x2000` | `(0, +1)` |
| 下 `0x4000` | `(0, −1)` |
| 左 `0x8000` | `(+1, 0)` |
| 右 `0x10000` | `(−1, 0)` |
| 左上 `0x200` | `(+1, +1)` |
| 右上 `0x400` | `(−1, +1)` |
| 左下 `0x800` | `(+1, −1)` |
| 右下 `0x1000` | `(−1, −1)` |

八个位**各自独立**，同时按下就逐个相加，最后统一归一化。

### 1.2 归一化规则（本版最关键的一条）

> **只有长度超过 1 才被压回 1；不超过 1 就原样保留。**

- 数字方向键：分量是整数，非零时长度至少是 1，所以**键盘走路永远是满速**，方向发生变化但速度不变。
- 模拟向量：长度 `≤ 1` **原样透传** ⇒ 摇杆推一半就是半速（真正的亚单位慢走）；长度 `> 1` 才被压成单位长。

这条规则解释了当前版本对 `1.21.21` 之前「模拟斜走能超过单位圆」的封堵方式：**单向钳位**——低了不管，
高了压到 1。

顺带一提：代码里还有一处 `0.0001f` 的「太短就当 0」判断，但两条分支在到达它之前已经保证了长度
要么 `>1`、要么是整数长度 `≥1`，所以它**永远不会触发**。它不是一个摇杆死区。

### 1.3 有没有摇杆死区？

**分两层看，别混为一谈：**

- **移动合成这一层（把输入变成 `mMove` 的地方）没有任何死区、轴向重映射或非线性重标定。**
  这一层唯一的模拟处理就是上面那条「长度 > 1 才压回 1」。
- **手柄/触屏的硬件前端（摇杆轴读进来、送进合成层之前的那一段）在 1.26.51.01 里还没定位到。**
  这一段完全可能带死区（手柄死区是裸数值常量，不需要任何字符串或选项名），
  本机也没有手柄和触摸屏可以实测，所以**不能断言「游戏里没有死区，死区一定来自驱动」**。

一句话：**能合成进 `mMove` 的值不会再被裁剪；但「摇杆从 0.01 推到 0.1 会不会被吃掉」这个问题，
本版还没有答案。**（`1.26.51.01` 没有 `XInput`/`GameInput` 导入，`left_stick_up/down/left/right`
只以方向动作名出现，前端链不在本轮可定位范围内。）

## 二、三向斜走：键盘做不到，只有混用时才可能

### 2.1 纯键盘：永远只有 8 个 45° 方向

实测 14 种组合（逐项回读输入向量）：

| 按住的键 | 输入向量 | 角度 | 与单键比的速度 |
| --- | --- | --- | --- |
| `W` | `(0, +1)` | 正前 | 1.00× |
| `A` | `(+1, 0)` | 正左 | 1.00× |
| `W+A` | `(+0.7071, +0.7071)` | 45° | **1.00×（没有 √2 加成）** |
| `A+D` | `(0, 0)` | — | 不动 |
| `W+S` | `(0, 0)` | — | 不动 |
| `W+A+D` | `(0, +1)` | **正前** | 1.00× |
| `W+S+A` | `(+1, 0)` | **正左** | 1.00× |
| `W+S+D` | `(−1, 0)` | **正右** | 1.00× |
| `W+S+A+D` | `(0, 0)` | — | 不动 |

两个结论：

1. **三键同按不会更快**，它会精确抵消掉一对反向键，退化成单键（`W+A+D` 就是纯 `W`）。
2. **斜走不加速**：`W+A` 的两个分量各是直行的 `0.7071` 倍，合速与直行一模一样。基岩版的斜走增益
   不来自输入向量（输入先被归一化了），要找加速得去看移动解算那一侧。

### 2.2 非 45° 角从哪来

八个方向位里，四个正交位（上下左右）由**键盘**注册，四个对角位由**触屏 D-pad 的四个角键**注册。
所以：

- 纯键盘只点亮正交位 → 只能组合出 45° 的倍数；
- 纯触屏 D-pad 一个角键只点亮一个对角位 → 还是 45°；
- **触屏角键 + 键盘方向键同时按**（或触屏多点同时按角键与正交键）：两个位一起点亮 → 相加得到 `(1, 2)`
  这样的向量，归一化后是 `(0.4472, 0.8944)`，角度 **26.565°**。

这就是「三向斜走」在当前版本唯一可复现的定义：**三个输入位（一个对角 + 两个正交，或一个正交 + 两个对角）
同时点亮，得到一个不在 8 向集合里的角度**。

| 点亮位数 | 归一化前 | 结果角度 |
| --- | --- | --- |
| 一个正交 + 一个对角（**两个位就够**） | `(±1, ±2)` 或 `(±2, ±1)` | `26.565°` / `63.435°` |
| 两正交 + 两对角（四位、无对冲） | `(±1, ±3)` / `(±3, ±1)` | `18.435°` / `71.565°` |
| 两正交 + 一对角（两正交已同向） | `(±2, ±2)` | 仍是 `45°` |

> **可复现性提醒**：这条路径需要触摸屏 + 键盘，或触屏多点。用鼠标键盘的 PC 玩家在正常操作下**到不了**
> 26.565°，`W+A+D` 之类的「三键」在输入层就塌缩成正交单键了。本文作者没有触摸设备，
> 26.565° 一类数值是从反汇编的整数加法和归一化推出来的，没有上机验证过。

### 2.3 对疾跑、潜行的影响

- 疾跑判定看的是**单位向量与视角的夹角**（±45° 扇区），而输入向量本来就是单位长，所以方向对了就能疾跑，
  与「有几个键在按」无关。
- 潜行把整条输入向量乘 `0.3`（附魔迅捷潜行 `0.3 + 0.15 × 等级`）；模拟输入的亚单位系数与它是**相乘**关系：
  摇杆推一半 + 潜行 = `0.5 × 0.3 = 0.15`。

## 三、视角灵敏度

### 3.1 三端共享一条曲线

设置里键鼠 / 触屏 / 手柄的「灵敏度」滑块共用同一个取值，先过一条公共曲线：

```
v = 0.81 × (1.1 × S) ^ 0.6125          S = 滑条值（0..1），v = 参与后续公式的灵敏度
```

- `S = 0` → `v = 0`
- `S = 0.5` → `v ≈ 0.5616`
- `S = 1` → `v = 0.81`

曲线是**小于线性**的（指数 0.6125），所以低灵敏度区间分辨得更细，高灵敏度区间增长放缓。
这三个常数（`1.1`、`0.6125`、`0.81`）在整个可执行文件里各只出现一次。

### 3.2 键鼠：像素 → 角度

```
Δyaw(度) = dx × 9600 × (0.15 + 0.6 × v)³ × 0.3 ÷ W
Δpitch(度) = dy × 9600 × (0.15 + 0.6 × v)³ × 0.3 ÷ W
```

- `dx`、`dy` 是鼠标的像素增量；
- `W` 是**渲染宽度的物理像素数**（和窗口高度、对角线、系统缩放都没关系）。

**分辨率无关性验证**：同一台机器把窗口拉窄，每像素转过的角度严格按宽度反比变化，
「每像素角度 × 宽度」恒为 `332.61`（`S = 0.5` 时）。只改窗口高度时该值完全不变。

代入 `S = 0.5`、`W = 2559`：**约 `0.1300°/像素`**，横向和纵向**完全相同**。
（代码里另有一个只乘竖直（俯仰）的 `0.7` 因子，门控是布尔选项 **`hotbar_only_touch`**——也就是「触屏专用 HUD」
那个开关，而不是 `InputMode`。默认关闭，所以默认键鼠配置下横向和纵向速度相同——实测 `dy` 与 `dx`
的每像素角度一致到 `1.5e-5°`。）

灵敏度换了，速度会跟着曲线走：`S` 从 `0.5` 降到 `0.2`，每像素角度从 `0.1300°` 降到 `0.0451°`
（比值 `0.347`，与曲线预测的 `0.347` 吻合）。

> 注意：改完灵敏度要**重启游戏**才生效。通过选项文件热改只会写进存档，正在跑的会话不会重新计算。

### 3.3 望远镜

开镜后视角速度按下面这条式子缩放（`D` 是设置里的「望远镜阻尼」，0~1 小数，默认 `0.5`）：

```
D ≤ 0.05  →  1.0        （不阻尼）
D > 0.05  →  0.05 / D   （越往上调越慢）
```

换成百分数就是 **`D ≤ 5% → 1`、`D > 5% → 5 / D`** —— 正是社区 Wiki 一直写的那条公式。
代码里的比较点是 `0.05f`，所以 `5%` 是硬阈值。

四点实测（每点都改 `options.txt` 重启后测，`dx=100 px`）：

| `D` | 未开镜 | 开镜 | 实测倍率 |
| --- | --- | --- | --- |
| `0.0` | `4.510147°` | `4.510132°` | `0.9999966` |
| `0.04` | `12.992554°` | `12.992554°` | `1.0000000` |
| `0.5` | `12.992554°` | `1.299271°` | `0.1000012` |
| `1.0` | `12.992554°` | `0.649628°` | `0.0500000` |

`0.04` 和 `0.5` 正好落在阈值两侧，倍率从 `1.0` 直接跳到 `0.1` —— 阈值就是 `0.05`，没有中间态。
开镜期间 `ItemInUse` 组件存在、松手立刻恢复原速，不会残留。

### 3.4 俯仰（Pitch）钳位

视角上下限是 **`−89.9°` 到 `+89.9°`**，但不是简单的两次 `clamp`：

- 下限是精确的 `−89.9f`（`0xC2B3CCCD`）；
- 上限走的是「离地平线至少 `0.1°`」的写法，`float32` 往返之后落在 `89.89999389648438`（`0x42B3CCCC`），
  比 `89.9f` **低 1 个 ULP**。

所以用脚本读回来的极限值会是 `+89.899993896…` 和 `−89.900001525…`，这不是测量误差。
偏航（Yaw）另有 `fmodf(angle + 180, 360) − 180` 的折回，永远落在 `[−180°, +180°)`，
正常玩法累积不出多圈角度（详见 [`angles-wiki.md`](angles-wiki.md)）。

## 四、速查表

| 问题 | 答案 |
| --- | --- |
| 摇杆推一半会不会慢走？ | 会，半推 = 半速（长度 `≤1` 原样保留） |
| 摇杆推到底再斜着推，会不会超过满速？ | 不会，长度 `>1` 一律压成 1 |
| 键盘斜走比直走快吗？ | 不快，都是满速，只是方向不同 |
| `W+A+D` 会更快吗？ | 不会，等价于只按 `W` |
| 三向斜走存在吗？ | 存在，但需要「触屏角键 + 键盘」或触屏多点混用；纯键盘不可能 |
| 摇杆有死区吗？ | 合成层没有；手柄/触屏硬件前端是否有死区**未定位**（本版无手柄可实测） |
| 灵敏度怎么换算成角度？ | `Δ = 像素 × 9600 × (0.15+0.6v)³ × 0.3 ÷ 渲染宽度`，`v = 0.81(1.1S)^0.6125` |
| 开镜慢多少？ | `min(1, 0.05 / D)`：`D≤5%` 不阻尼，`D>5%` 按 `5/D` 减速（默认 `D=50%` → `0.1×`） |
| 抬头能到 90° 吗？ | 不能，上限 `89.9°`（浮点上比 `89.9f` 低 1 ULP） |
