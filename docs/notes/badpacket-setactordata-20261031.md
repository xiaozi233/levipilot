## 3. `error_value = 104` 的语义（本轮新闭合）

**`104 = std::errc::bad_message`（generic 类别，即 UCRT `EBADMSG`）**，意思是“数据不是有效的”。

推导链（可复用，全部静态）：

1. 记录里的 `category` 是 `&std::error_code::category()`，即类别对象地址。用当轮
   `module_base`（`out/diagnostic-full-final-violation.json` 的
   `observation[].reply.module_base = 0x7FF6AACC0000`）换算：
   `rva = category - module_base = 0xE6ABB80`，落在 `.rdata`。
2. 该地址第一个 qword = `0x14E6ABB90`（静态 VA），即真正的类别对象在 `rva 0xE6ABB90`；
   其后是 vtable：`0x1400FB550`（dtor）、`0x140108400`（`name()`）、
   `0x140108410`（`message(int)`）。
3. `name()` 直接返回字符串 **`"generic"`**；`message(int)` 走 `std::_Syserror_map(a3)`
   —— 正是 MSVC 的 `std::generic_category()`。
4. 因此 104 是 **POSIX/`std::errc` 域**的值，不是 Win32 错误码。
   Windows SDK `10.0.26100.0/ucrt/errno.h`：`#define EBADMSG 104`，
   对应 `std::errc::bad_message`。

> 注意：类别指针是**进程内地址**，换了进程/基址就没有意义；必须和当轮 `module_base`
> 一起记录才能换算。文档里不要写成可移植枚举。

## 6. 读侧已闭合到函数级（2026-11-01 追加）

`[代码]` `SetActorDataPacketPayload` 的虚表与实现（静态 VA，`image_base=0x140000000`）：

| 槽 | 成员 | 地址 | 说明 |
| --- | --- | --- | --- |
| +0x08 | `getId()` | `0x143DF6E20` | 返回 **39** |
| +0x10 | `getName()` | `0x143DF6E30` | `"SetActorDataPacket"` |
| +0x18 | `getMaxSize()` | `0x140C44940` | 10 MiB |
| +0x20 | `checkSize()` | `0x1416C20F0` | 超限报 115（同类别） |
| +0x28 | `writeWithSerializationMode` | `0x143DF6E50` | `if (mode == 5)` 走 cereal |
| +0x38 | `write(stream)` | `0x140C43F60` | |
| +0x48 | `read(stream)` | `0x143DF7060` | 调 `_read`，失败时按流状态改成 104 |
| +0x60/+0x68 | get/setSerializationMode | `0x143788CD0`/`0x143788CE0` | 读写 payload`+136` |

- `read(stream)` 的失败分支（`0x143DF7362`）就是 `v28 = 104`：
  条件等价于 SDK 公开头的
  `ReadOnlyBinaryStream::ensureReadCompleted()` —— **`mHasOverflowed || mView.size() != mReadPointer`**
  ⇒ `std::errc::bad_message`。所以 104 的语义是“**读越界或有剩余字节**”，不是普通的 EOF。
- `_read(stream)`（`0x143DF7CC0`）开头 `if (getSerializationMode() != 5)` 会用**同一条** 104
  但配另一条消息（“Packet defined using SerializationMode::CerealOnly tried to serialize
  (read) using a different mode: {}”）。现场 context 是 `BinaryStream read() incomplete…`，
  说明**模式门禁在读取侧通过了**，失败发生在随后的字段读取里。

### 构造函数把模式钉成 CerealOnly

`[代码]` 构造 `SetActorDataPacket`（`0x1416B4320`）时 `mov dword ptr [rdi+98h], 5`：
`0x98 = payload(+0x10) + 0x88`，正是 `getSerializationMode()` 读的 `payload+136`。
即**新建实例默认 5 = CerealOnly**，读写都会走 cereal，表面上是自洽的。

### 由此得到的候选机制（按当前证据排序，均未定案）

1. **写入用了另一种模式**：`writeWithSerializationMode(stream, ctx, override)` 的第四参带
   “可选 override”（`a4 & 0x100000000`），上层可以按一次发送覆盖模式，而**不改对象自己的字段**；
   读取端用的是新建实例的默认 5。若发送侧被 override 成经典二进制，接收侧按 cereal 解析
   同一段字节 ⇒ 计数读成垃圾 ⇒ 越界 ⇒ 104。`setSerializationMode` 只有虚调用点（无直接 caller），
   与“上层按需设置”一致。
2. **载荷被截短**：写入侧实际写出少于读取侧 schema 所需的字节（34 字节里字段没写完）。
   单机走 loopback，仍经过长度前缀的传输层，因此不能仅凭“同进程”排除。

**判别方法（下一次复发）**：发送侧 tap 的 B3 白名单能序列化指定 id 的字节
（`packet_capture(True, ids=[39], serialize_ids=[39], directions=["send","recv"])` +
`packet_bytes`）。抓到的 39 号载荷：前 8 字节若是小的 runtime id（如 `01 00 00 00 …`）
⇒ 经典二进制（指向机制 1）；若是哈希/指纹形态 ⇒ cereal，再比对长度与 34（指向机制 2）。

**接线建议（未落地，避免与另一会话正在重写的 `check_flight`/`ViolationObservation` 冲突）**：
在 `LEVIPILOT_VIOLATION_DUMP` 生效时，于 `check_flight` 开头 arm 上面这条 capture，
在它的 `finally` 里 `packet_bytes(0, 256)` 落盘到 `<dump>.bytes.json`，再 `packet_capture(False)`。
能力本身（序列化 39 号、导出字节）已验证可用，缺的只是这两处接线。

本轮未做：不对 39 号抓包（未复发），不构造畸形包。

## 8. 接收侧钩子尝试（失败并回退）+ `packet_size` 语义（2026-11-01 01:1x）

### 尝试与结果

目标：在解析入口记录每个入站包的切片长度。选了 `Packet::readNoHeader`（每个客户端入站包都过它）。

- `[代码]` 静态确认目标地址：分发函数 `sub_1416AB0E0` 在 `0x1416ABE4F` 调
  **`sub_1416C2310` = `Packet::readNoHeader`**。反编译签名是
  `(__int64 sret, _BYTE* this, stream, ctx, subid)` —— 即 `Bedrock::Result<void>` 用
  **隐藏返回指针（sret）**，`this` 在第 2 个寄存器。
- 两次现场都崩（新增 `crash-36456`、`crash-21624`，异常 `0xC0000005`，`last_command=violation_watch`），
  第一次在加“有界自旋等 origin”后仍崩 ⇒ 不是安装窗口问题，是 **wrapper 与真实 ABI 不符**
  （`Bedrock::Result<void>` 在本仓库 SDK 头里的返回约定与真实二进制不同）。
- 处置：**整段入站钩子已回退**（`inbound_drain` 现在明确回
  `{"supported": false, "reason": "read_no_header_hook_retired"}`，不再假装有数据）。
  回归：安装/停止守望恢复正常（`callback_hooked/screen_hooked` 都对，`hits=0`），无新崩溃。

### `packet_size` 语义不必再赌

样本 C 里 188 的发送侧序列化恒为 **5** 字节，而违规回调的 `packet_size = 2`。两种可能语义都指向同一结论：

- 若 `packet_size` 是**包体长度** ⇒ 2 < 5，包体被截短；
- 若 `packet_size` 是**含包头的整包长度** ⇒ 整包 2，包体更短，同样被截短。

包头只会**增加**长度，不可能把 5 变 2。所以"**到达读侧的帧比发送侧序列化结果短**"这一结论
不依赖 `packet_size` 的精确口径。

### 下一步（不再做新钩子）

用已落地的 **发送侧全量身份环**（`packet_capture(directions=["send","recv"])` 不过滤 id，
导出 `<dump>.drain.json`）检查失败 tick 附近的**包序列**：如果失败的 39/111/188 之前紧跟
187（UpdateAbilities，发送侧恒定 33 字节），就说明是**能力包把帧边界读歪**，后续包在错误偏移上
被解析——这也解释了为什么失败包 id 每次不同。这条只用已有设施，不需要新钩子。

## 9. 入站切片长度：截短层已定位（2026-11-01 02:0x）

### 能力（已落地、已验证稳定）

`violation_watch on` 同一开关还装第三只只读钩子：`Packet::readNoHeader` 的**原始机器形态**
（5 个指针参数，无寄存器返回）。关键实现要点：

- 早期两次崩溃的原因：按 `(Packet*, stream, ctx, subid)` 写的 typed wrapper 与真实 ABI 不符；
  改成**五个 `void*` 原样透传**后才稳定。
- 不假设流在哪个参数：对前 4 个候选逐个用 `readMemory` 探测
  （`+0x28 view / +0x30 size / +0x38 readPtr / +0x40 overflow`），
  `0 < size <= 1MiB && readPtr <= size` 才算命中。实测 **流恒在 r8（第 3 个参数）**。
- 采样 1/4，环形 1024 行；`inbound_dump {"path": ...}` 由 **mod 直接落盘**
  （多客户端共用管道时回复会被另一个连接截走，所以结论不依赖谁在听）。
- 试图再读包 id 时（对校验过的候选调 `getId()`）又崩一次（`crash-11356`），
  已移除该读取——id 由违规回调那边给出，不需要在热路径里虚调用。

### 实测对照（同一次 `--flight-only` 运行，4 份 dump 同时产出）

| 项 | 值 |
| --- | --- |
| 发送侧 B3 序列化 | 187 = **33**、188 = **5**、111 = 13–26 |
| 入站切片长度 | 187 → **35**（39 次）、188 → **7**（23 次） |
| 结论 | **入站切片 = 发送侧 payload + 2**（这 2 字节是 187/188 的 id varint；见 §12 更正） |
| 失败样本 C | 188 的 `packet_size` = **2**，同模型应为 **7** ⇒ 少了 5 字节 |

### 定位结果

`[实测]` 失败包到达**解析入口时切片已经只有 2 字节**，而写侧输出 5（+2 头 = 7）。
所以截短发生在**解析器上游的帧切分/解压/传输层**，不在 payload schema、不在 cereal 反序列化、
也不在本次钩子所在的边界之后。这与此前"三次失败横跨 39/111/188"一致：
读侧只是受害者，受损的是帧边界。

### 仍未定（下一层）

帧头里**声明长度**与**实收字节**谁先错：若声明长度本身是 2（写侧头错），则是发送侧分帧 bug；
若声明 7 而只到 2（传输截断），则是传输层。判别需要在**解包/解压边界**再取一次
（缓冲区长度 vs 头声明长度），又是一次全新钩子；本轮已因同类钩子产生 3 个 crash 文件
（`crash-36456`、`crash-21624`、`crash-11356`），未继续。

## 10. 子问题收束：声明长度 vs 实收字节（2026-11-01 02:1x）

### 已知（`[实测]`，同一运行对齐）

- 入站切片 = 发送侧 payload **+2**：187 33→35、188 5→7（各 39/23 次）。
- 失败样本 C：188 的入站 `packet_size` = **2**（同模型应为 7）。

### 两个剩余子情形

| 子情形 | 含义 | 需要的观测 |
| --- | --- | --- |
| A | 帧头里**声明长度就是 2** | 发送侧分帧 bug（写侧头与 body 不一致） |
| B | 声明 7，但传输只到 2 | 传输/解压层截断（批尾被剪） |

### 现有证据更偏向 A（`[推断]`，不是定案）

1. 读侧是在**逐包解析**阶段失败的（`read() incomplete` / `overflow`），而不是批处理层的
   长度校验失败。若整批字节比声明少，连接层会先报批级错误。
2. 失败前同一批里的更早包都解析成功（我们的身份环在失败 tick 前有连续的入站切片记录），
   说明这批字节按“每包声明长度”切分是自洽的，只是这一个包的声明长度与 body 不符。
3. 反证：若属 B（批尾被剪），被剪的应当是批中**最后一个**包。三次失败横跨 39/111/188，
   若都为批尾巧合，概率不低但无法排除；这一点没有证据。

### 要变成定案，只需一处仪器

在**解包/解压之后、逐包切分之前**记录 `(批总长, 首个声明长度, 剩余字节)` 三元组，
与本次的入站切片（187→35、188→7）对齐即可二分。实现要点（沿用本轮已验证的形态）：

- 用**五个 `void*` 透传**的原始机器形态钩子，不做 typed 包装（typed 版崩过两次）；
- 不对候选做虚调用（读包 id 的那次崩了第三次，已移除）；
- 所有读取走 `readMemory` + 范围校验（`0 < size <= 1MiB`）；
- 结果由 mod 直接写文件（多客户端时管道回复会被另一连接截走）。

本轮未再装这只钩子：同类钩子已产生 3 个 crash 文件（`crash-36456/21624/11356`），
在无法离线验证其 ABI 前继续加钩子的风险高于收益。

## 11. 决策：子问题不阻塞任何自有代码动作（2026-11-01 02:2x）

再往下钉“声明 2 还是实收 2”，需要在**游戏自己的**批处理/解压路径里再插一只钩子：

- 该函数族（`sub_1419D7D90` → `sub_1416AA7F0` → 分发 `sub_1416AB0E0`）属于 Bedrock 网络层，
  **不是本仓库的 mod 代码**；无论子问题是 A（发送侧分帧）还是 B（传输剪尾），
  mod 侧都没有可修的写入点——我们不写 `SetActorData` / `MoveDeltaActor` / `UpdateAdventureSettings`，
  也不碰批缓冲。
- 已定位的事实足以支撑这个判断：入站切片 = 发送侧 payload +2（187 33→35、188 5→7 各数十次），
  失败样本的 188 切片为 2；读侧报的是**逐包解析越界**而不是批级长度错误。
- 三次加钩子的尝试已产生 3 个 crash（`crash-36456/21624/11356`）。继续在未验证 ABI 的游戏内
  函数上加钩子，收益（一个不影响行动的子情形）低于风险。

因此本调查的结论停在：**根因层 = 游戏网络栈的入站分帧/解压/传输，早于包解析；mod 侧无缺陷、无补丁**。
需要彻底定案时的仪器与步骤见 §10，可作为后续独立任务执行。

## 13. 声明长度**不在**切片前（实测否定）+ 判定方法保留（2026-11-01 03:2x）

### 实测：切片是拷贝，前面的字节不是长度前缀

`out/inbound-slices-before.json`（57 条，重装后同一进程）：

```
id=111 size=23  before 0000000000000000 8000cc811c020000   slice 6f15 01fea1a4...
id=144 size=24  before 10e668941b020000 10d678941b020000   slice 9001 006808bfc0...
id=39  size=17  before 0000000000000000 8000cc811c020000   slice 2706 010007078080...
```

- 切片前 16 字节是**堆指针 / 零**（`0x21b…` 两枚指针、`0x21c81cc0080` 一类），
  末尾字节恒为 `00`；若是帧头，长度 varint 的末字节必须正好结束在切片起点，
  且值等于 body（这里 16/20/22），实际不是。
- 结论（`[实测]`）：解析入口拿到的是**独立拷贝**（或指向另一对象内部），
  帧的 `length` 前缀既不在切片里，也不在切片前可读的位置。`before_hex` 保留为
  “现状证据”，但**不能**用来恢复声明长度；`slice_verdict()` 因此把 `declared==0`
  一律判 `unknown`，自检遇到“声明不可读”时 skip 而不是误判。

### 仍然可用的判定事实（不依赖声明长度）

1. `[实测]` 发送侧 `packet.write()` 的 body：187=33、188=5（白名单序列化，多次运行恒定）。
2. `[实测]` 解析入口切片：187 = 35 = 33 + 2、188 = 7 = 5 + 2（+2 是两个 id 的 varint 宽度）。
3. `[实测]` 失败样本 C：188 的切片 = **2 字节**，即只有 id varint、body 为 0。
4. `[代码]` 本地世界是 loopback：`BatchedNetworkPeer::sendPacket` 实测 0 调用，
   `LocalNetworkPeer::$sendPacket` 仅 dllimport —— 发送侧没有可观测的“帧字节”，
   帧是在进程内由另一层写出的。

由 1+3 可直接得：**写侧明明有 5 字节 body，到达解析入口时 body 为 0**。
这已经是“帧长度与 body 不一致”，不需要再猜；剩下只差“谁写的 0”。

### 要定案还缺的一步（可选、独立）

需要钩住**写帧/切分**的那一层（不是 readNoHeader）才能看到“声明长度”这个局部值。
本轮已排除的候选与理由：

- `0x1416AA7F0`（runEvents 任务）/ `sub_1419D7D90`（网络运行循环）：不是逐包函数。
- `sub_1416AB0E0`（逐包解析循环）：入口处批还没解析，取不到每包的声明长度。
- 切片前 16 字节：实测为无关堆数据（见上）。

进一步静态追查需要完整反编译 `sub_1416AB0E0`（0x1e9f 字节，MCP 单次返回被截断），
以及 `off_14E75BD20`（ReadOnlyBinaryStream vtable）的写入者（`xrefs_to` 本轮两次超时）。
这属于“定案子情形”，不影响已经成立的行动结论（§11）：
**根因层在游戏网络栈的帧写出/切分，早于包解析；mod 侧无写入点、无补丁。**

### 现场验收项（`driver/selftest.py`）

`check_inbound_slices()`：切片行数 ≥4、id 落在合理范围、至少出现一个已知 id
（39/111/144/187/188）、以及“声明==实收”占比（≥90% 才通过；声明不可读即 skip）。
它验证的是**仪器已接通**（切片字节 + 前导字节都能读到），不是“某次没有违规”。

## 15. 闭合证据：失败切片里装着**别的包的 payload**（2026-11-01 13:06，tick 1881）

这是第一次同时拿到「失败切片字节 + 同 tick 发送侧 body + 完整错误文本」的一次复现。

### 现场

```
seq 3153  tick 1881  size 35  id 187  bb01 01000000ffffffff0204010100ffff0f00ff00...
seq 3154  tick 1881  size 23  id 188  bc01 0000000001 0e 01 00 07 07 80 80 c0 84 80 83 80 03 00 00
```

- 回调行：`packet_id=188`、`packet_size=23`、`error_value=104`、
  `context="BinaryStream read() incomplete
readNoHeader failed! packetId: 188"`（完整，未截断）。
- 同 run 的 188 正常切片：**61 条，全部 7 字节**（`bc01` + body `0000000001`）。
- 发送侧 `packet.write()` 的 188 body：**63 条，全部 5 字节**。

### 失败切片的构成（`[实测]`）

| 段 | 字节 | 长度 |
| --- | --- | --- |
| 包 id（188 的 varint） | `bc 01` | 2 |
| 188 自己的 body | `00 00 00 00 01` | 5 |
| **外来 16 字节** | `0e 01 00 07 07 80 80 c0 84 80 83 80 03 00 00 00` | 16 |

外来 16 字节与同 run 的 SetActorData(39) 切片逐字节同构：

```
正常 39 切片 (17B)：27 0d 01 00 07 07 80 80 c0 84 80 83 80 03 00 00 00
外来 16 字节      ：   0e 01 00 07 07 80 80 c0 84 80 83 80 03 00 00 00
```

即：**一个 39 包的 payload（演员 runtime id 0x0e + 15 字节），不带它自己的 id 字节 0x27**，
被塞进了 188 的帧里。

### 结论（子情形闭合）

1. `[实测]` 交付到解析入口的切片**长 23 字节且内容完整**：前缀是合法的 188 头 + body，
   尾巴是一段连贯的 39 payload。**没有“被剪掉”的迹象**——被剪的切片不会留下完整的邻居 payload。
2. `[实测]` 切片长度（23）与回调的 `packet_size`（23）一致，说明游戏自己也知道这个帧是 23。
3. ⇒ **不是传输/解压剪尾，而是帧写出侧把邻居包的 body 并进了这个帧**（长度也随之变成 23）。
   结合 §14 的 187（36 vs 35）与更早样本 C（188 只有 2），同一层的表现是“帧长度与 body 不一致”，
   只是方向不同。
4. `[实测+代码]` 该层的后果：解析入口 `readPtr = 2`（调用方已读掉 2 字节 id），
   188 的 body 只有 5 字节，读完还剩 **16 字节未消费**；
   `ReadOnlyBinaryStream::ensureReadCompleted()` 的判据是
   `mHasOverflowed || mView.size() != mReadPointer`，两种方向（少读/多读）都给
   `bad_message(104)`、文本同为 `BinaryStream read() incomplete.` —— 这解释了为什么
   样本 C（切片 2 字节，短）和本次（切片 23 字节，长）报的是**同一个** error 104。
   之后 `handlePacketViolation(response=3)` → `BadPacket(90)` → 错误页
   `ClientDisconnection-90` / codeword `Block`。

### 仍是推断的部分

1. 帧头长度字段本身的值：入站侧只能间接推断（§17 的分布对比给出**倾向 23**的旁证，
   长度 varint 未被直读，未定案）。
2. 责任归属：`[实测]` 已证否“传输剪尾”（剪尾不会留下连贯的邻居 payload），
   也证否“本仓库直接写这些包”；但**未排除**对象共享、时序、以及自有 hook ABI 的间接影响。
   结论只能写到：疑点集中在组帧路径，具体写入点与责任归属未闭合。

### 复现配方（可重复）

1. `dev.py run --world "超平坦测试" --allow allow_hook_va=1 --allow allow_packet_capture=1`
2. `selftest.py --flight-only`（或 `--violation-only` 后再跑 flight），每轮 20–60 秒；
3. 约 **1/6 概率**命中；命中后 `inbound_dump` + 违规 dump 同 tick 对齐。

## 17. 旁证：帧声明值**倾向** 23（2026-11-01 13:5x；未定案）

### 判别原理

切片大小来自帧自己的长度字段（切分器按每包长度切），所以
**只要证明“切片 == 该包自己的长度、而不是“批里剩下的字节””，失败切片的 23 就直接等于帧声明值。**

### 证据：多包 tick 里第一个包的切片长度不变（`[实测]`）

把 1662 条入站切片按 tick 分组（386 个 tick 有 ≥2 个包），比较“多包 tick 的首包”和
“单包 tick”的尺寸分布：

| 包 | 多包 tick 首包尺寸 | 单包 tick 尺寸 |
| --- | --- | --- |
| 187 | 35 ×45 | —（未单独出现） |
| 188 | 7 ×29 | — |
| 111 | 21×58, 22×50, 23×26, 14×21 | 21×37, 22×23, 23×16, 14×15 |
| 144 | 95×87, 94×20 | 95×226, 94×68 |
| 39 | 17×29, 18×3 | 17×2 |

若切分器用“批里剩余字节”，多包 tick 的首包必然比自己的包大（187 会变成 35+后续包，
188 会变成 7+后续包）。实测完全相同 ⇒ **切片长度 = 该帧声明的长度**。

### 结论（`[推断]`，待直接读取长度前缀）

> **前提**：这条推断依赖“切分器直接使用帧声明长度作为切片长度”这一个假设。
> 多包 tick 的分布只证明**切片长度独立于后续包**，没有直接读到长度字段本身；
> 因此下面第 1 条是旁证，不是定案。

1. `[推断]` 失败 188 的切片是 23 字节，若切分器按声明长度切，则声明值 = 23（不是 7）。
2. `[实测]` 23 = 7（188 自己的 id+body）+ 16（一段完整的 SetActorData payload，演员 0x0e）。
3. ⇒ 不是“长度 7、传输多塞了 16 字节（未被计入）”；而是**写出侧把这 16 字节算进了帧长度**。
   两种描述里，可观测的事实是：**帧声明并携带了邻居包的 payload**。
4. `[实测]` 这 16 字节不是缓冲区残留：事发前一个包是 187（abilities payload），
   若为复用缓冲区的旧内容，这里应当出现 187 的字节而不是一条自洽的 39 payload。

### 负结果（有界搜索）

尝试直接读“声明字节”的两种途径都失败了，记录以免重复：

- 解析入口的四个指针参数里没有父流（父流 `view+readPtr` 应等于切片起点，1662 条中 0 命中）；
- 以内容匹配扫描调用者栈 ±0x600/0x800 字节，0 命中 ⇒ 逐包流确实是**独立拷贝**，
  批流不在该栈窗口内（大概率在连接对象堆上）。

因此“声明值”目前只能由尺寸对比推出。要定案仍需**直接读到长度 varint**，两条可行路径：
(a) 在切分函数里定位长度解码点并读出该局部值；(b) 拿到批缓冲（父流）并解析帧头。
两条都还没做成。

## 18. 追声明字节：三条新路径全部为负（2026-11-01 14:2x）

上一轮把“声明长度 = 23”留作旁证，这一轮专门去拿那个字节，三条路都走不通：

| 路径 | 做法 | 结果 |
| --- | --- | --- |
| 流对象里的源指针 | 逐包流若是拷贝，源指针可能作为普通字段留在对象前 0x60 字节；按内容匹配找“以切片首 4 字节开头的指针” | 801 条采样 **0 命中** |
| 调用者栈窗口 | 以返回地址槽为基准扫 ±0x600/0x800 字节，同样按内容匹配 | **0 命中** ⇒ 逐包流是独立拷贝，批流不在该窗口 |
| 第四个参数 `r9 = [rsi+0x208]` | 直接取该指针处 24 字节 | 是**带 vptr 的对象**（`0x7ff6c993bbd0` + 两个相差 0x10 的堆指针），不是原始批缓冲 |

另确认：**NetherNet 是静态链接进 exe 的**（版本目录与进程模块表都没有独立模块），
所以组帧代码确实在这份 IDB 里；但承载它的 `sub_1416AB0E0` 有 353 个基本块，
MCP 的 `decompile` 对 >64KB 输出截断到 1KB，而该函数内既无 `shl` 也无 `and 7Fh`
常量（`func_profile` 的 293 个常量里没有 127/128），说明**长度解码不在这个函数里**。

### 由此得到两个互斥模型（都未排除）

| 模型 | 含义 | 现状 |
| --- | --- | --- |
| A. 有长度前缀且算成 23 | 组帧时长度字段覆盖了 16 字节邻居 payload | 与“多包 tick 首包尺寸 = 自身长度”相符 |
| B. 没有长度前缀，23 就是缓冲长度 | 缓冲区里残留 16 字节旧内容，长度按缓冲算，所以“长度正确但多写了” | 与“切片是独立拷贝、前邻字节是堆数据”相符 |

两个模型的差别是“有没有那个前缀”，而这需要拿到**批缓冲**或**组帧函数**；
入站侧拿不到（上表三条路径），发送侧的 tap 又只看到 `packet.write()` 的 body。
**因此“声明 23 vs 7”这一问在本轮无法闭合**，只能写到“疑点在组帧路径，且两种形态都属于写侧”。

### 一条与此相关的旁证

`packet_capture` 的 tap 在同一 run 里记录了 111/187/188，却**没有任何 39**——
说明 SetActorData 的下发不走 `LoopbackPacketSender::sendToClient` 那条被 tap 的路径。
若模型 A 成立（188 帧里并入了 39 的 payload），两者必然共享了某段序列化缓冲，
而它们走的又不是同一条发送路径，这一点值得后续验证。

## 19. 找到切片流的构造点：`[代码]` 逐条读到（2026-11-01 14:4x）

读出来的结论：

### 这一步把问题推进到哪

- 可以确定：解析层没有“先读长度前缀再切包”的动作，它只是把 NetworkSystem 里某个 `std::string`
  的 `{ptr,size}` 包成流。**所以 §18 的模型 B（无前缀、长度即缓冲长度）在解析层成立。**
- 仍未定：那个 `std::string` 是谁写的、写的时候 size 为何是 23。
  上游若按 `[len][payload]` 从批里拷贝，则前缀确实存在（模型 A），只是不在这层读；
  若它是复用缓冲且只写了 7 字节却把 size 设成 23，则是模型 B 的“长度按缓冲算”。
- 下一个可执行步骤：找 `NetworkSystem + 0x128` 这个 `std::string` 的写入点（`sub_140670C40`
  之后到解析之间的调用链，或网络接收线程里的 `assign/append`）。

## 20. 模型判据翻转：切片缓冲是**复用**的（2026-11-01 14:5x）

对已有三份 dump 用切片数据指针（`category`）统计：

| dump | 行数 | 唯一缓冲地址 | 相邻同址 |
| --- | --- | --- | --- |
| `pb15-6.inbound.json` | 1024 | **2** | 805 / 1023 |
| `auxprobe.json` | 817 | **2** | 569 / 816 |
| `sourceprobe.json` | 801 | **2** | 545 / 800 |

结论：逐包流不是“每包一份新缓冲”，而是**同一个 `std::string` 缓冲反复复用**，
每次只改 size/内容。这与 §19 的构造点一致（流直接指向 NetworkSystem 成员 string 的缓冲）。

### 这条数据推翻了什么

§15/§17 曾用“事发前一个包是 187，若是残留就该出现 187 的字节”来排除缓冲残留。
**该论证不成立**：缓冲区由**生产者**写入、由解析器读取，两者之间存在交接；
对同一个复用缓冲而言，`188` 写入前最后落进去的不一定是解析器刚处理过的那个 `187`，
而可能是生产者更早放入的一段 SetActorData 内容。因此“16 字节是残留”重新成为**同等级候选**。

### 两个模型的最新状态

| 模型 | 支持证据 | 反对/未决 |
| --- | --- | --- |
| A. 长度前缀算成 23 | 多包 tick 首包尺寸恒等于自身长度（切分按每包长度） | 解析层不读前缀（§19），前缀若存在只能在上游，未见 |
| B. 复用缓冲残留 16 字节 | 缓冲只有 2 个、约 80% 相邻复用（本节） | 残留内容与“解析器前一个包=187”不符；但真正的上一写入者是生产者，不可见 |

两者都归到同一个待定位对象：**`NetworkSystem + 0x128` 这个 string 的生产者写入点**。
下一步只有两条：把这个类型在 IDA 里建起来后追写入者，或在生产者线程钩住该 string 的 `assign/append`。

### 缓冲按方向分开（同一份 dump 的另一条切分）

按缓冲地址再切一刀：

| 缓冲 | 出现的包 | 线程 |
| --- | --- | --- |
| `0x23e7037a020` | **144 PlayerAuthInput** ×129 | 37408 |
| `0x23e90922020` | **111 MoveDeltaActor** ×640、**39 SetActorData** ×46、314 ×2 | 36796 |

即：上下行各有自己的复用缓冲，且 **39 与 111/188 共用同一个下行缓冲**（线程 36796）。
这让“失败 188 的尾部 16 字节原本是缓冲里一段 SetActorData”在**机制上成立**
——同一缓冲、同一线程、同一方向，39 确实写进这里过。

仍未解释的细节：若 39 以 `[id][payload]` 从偏移 0 写入，偏移 7 处应是 payload[6]=`80`，
而实测尾部以 `0e` 开头（payload[0]）。也就是说，残留说还需要“写入偏移不等于 0”
或“某次写入只落了 payload”这样的额外条件，尚未找到证据。

## 22. 抓到填充那次 memmove：源不是帧头（2026-11-01 15:2x）

### 实测（现场 5 条，`inbound_sample=1`）

结论：

1. `[实测]` `after` 全部以包 id 开头（`6f`=111），长度 21/22 与入站切片一致 ⇒ 拷贝源就是

- 模型 A（前缀算成 23）依然可能：上游按 `[len]` 切成 per-packet 缓冲时，len 可能是 23。

可以在 `memmove` 命中里再记录 `src-0x20..src` 的更多字节判池结构，或钩住返回这些源缓冲的

## 23. 第四次复现：失败 size（8）与拷贝长度（7）不一致（2026-11-01 15:0x）

### 现场

`[实测]` 同一进程、`inbound_sample=1`、`memmove_probe(id=188)` 打开：

```
callback: tick 252  packet_id 188  packet_size 8  error 104  response 3
screen  : tick 252  reason 90 / Block
memmove(188) 记录：tick 168/169/183 …，copy_len 全为 7
```

- `[实测]` 这次失败切片的 `packet_size` 是 **8**（188 的 id 2 + body 5 = 7，多 1 字节）。
- `[实测]` 同期 188 的 memmove 拷贝长度**全是 7**，与失败帧的 8 不符。
- `[实测]` 拷贝源缓冲是**复用的**（同址反复出现），且拷贝区之后紧跟着**上一个包**的字节
  （例：`bc01 0000000001 | 00 ff ff 02 04 01 01 00 ff` —— 7 字节之后是上一包 187 的残段）。

### 这条数据改变了什么

此前默认“解析流的 size 就是那次 memmove 写入的 size”。这次不成立：
**拷贝长度 7，解析看到的却是 8** ⇒ 在 `assign`（写 size）与构造流（读 size）之间，
size 字段还不是刚刚写入的值，或者被别的东西改过。

把它与历史样本放在一起：

| 样本 | 失败 size | 该包正常大小 | 差值 |
| --- | --- | --- | --- |
| 03:12 | 36 | 35（187） | +1 |
| 12:47 | 20 | —（111） | ? |
| 13:06 | 23 | 7（188） | +16 |
| 15:0x | **8** | 7（188） | **+1** |

差值不固定（+1/+16/−5），而且都围绕“该包正常大小”。这与**复用缓冲在写入与解析之间被并发访存**
（另一个线程写、解析线程读）最吻合：解析线程可能读到“新的几个字节 + 旧的尾巴”，
或读到上一包遗留的 size。

### 相应修正的结论

- 模型 A（帧声明 23）**进一步走弱**：若真有一个前缀声明，四次应当读到四个不同的合法值，
  而实测多是“正常大小 + 小偏移/大偏移”的混合形态。
- 模型 B（复用缓冲残留）**得到直接支持**：源缓冲确实在拷贝区之后保留着上一个包的字节（本次实测）。
- 新的候选根因：**解析缓冲 `ns+0x128` 这个 string 的写入与解析之间缺少同步**（竞态）。
  这能同时解释 size 与内容的不一致，也解释了“只偶发、约 1/6”。

### 工具事故与修复（记录）

钩 `memmove` 后连续两次把管道弄死（进程仍在、无 crash dump）。原因是 detour 内部
`readMemory`/环发布可能再次进入 memmove，形成递归。已加线程级重入保护，
复测同一场景 **管道存活**、检查 37/39（两次失败是 “fly: not_in_world”，即该 run 里世界已丢失）。

### 线程归属（同一次运行内）

同一次运行里按包分 tid：

| 包 | tid |
| --- | --- |
| 111 / 187 / 188 / 39（下行） | **33788**（同一个） |
| 144（上行） | 36128 |

即**下行所有包由同一线程解析**。早前 DR 命中记录到的 size 写入 tid 是 **36148**，但那是
另一个进程实例，跨实例不能直接比较。要判定竞态，必须在**同一次运行**里同时拿到
“写 size 的 tid”与“解析该包的 tid”——这是下一步唯一需要的测量（现有仪器已够：
DR 命中带 tid，入站行带 tid）。

## 24. 同线程否掉竞态；新样本显示缓冲在包中途用尽（2026-11-01 15:1x）

### 同一次运行内的 tid 配对（`[实测]`）

同一进程、`violation_watch(loop_addr)` + `inbound_sample=1` + `watch_set(net_ctx+0x138, w, 8)`：

| 观察 | tid |
| --- | --- |
| 写 `ns+0x138`（DR 命中，2000/2000 条） | **23848** |
| 解析下行包 111/187/188/39 | **23848** |
| 解析上行 144/72 | 30616 |

⇒ **写者与解析器同一个线程**。§23 的“并发写/读竞态”候选**被否**。
“size 与拷贝长度不一致”必须在**程序顺序**内解释，不是时序竞争。

### 新样本：tick 397，111 包 `packet_size = 5`（`[实测]`）

同 tick 的入站环尾部（`out/pair.json`）：

```
397 size 35 id 187  bb010100…
397 size 7  id 188  bc010000000001
397 size 14 id 111  6f160000000000011a0100000002
397 size 21 id 111  6f1401faa5c2c10001f859e5410000000100000004
397 size 23 id 111  6fbb01013d3e1dc10001b3063ec10001e10001000000
397 size 5  id 111  6f10000000        ← 失败帧
397 size 1  id 72   48
```

两点：

1. `[实测]` 失败帧只有 **5 字节**（`6f 10 00 00 00`），而 111 正常要 14–23 字节 ⇒ 流在**包中途用尽**；
2. `[实测]` 紧接着出现一个 **1 字节**的“包”（`48`，解出 id 72）⇒ 游标已经越过有效数据，
   读到了缓冲里的残余字节。

### 修正后的候选机制

把五次样本按方向排：

| 样本 | 包 | 失败 size | 该包正常 | 形态 |
| --- | --- | --- | --- | --- |
| 03:12 | 187 | 36 | 35 | 多 1 |
| 13:06 | 188 | 23 | 7 | 多 16（邻居 payload） |
| 15:0x | 188 | 8 | 7 | 多 1 |
| 15:1x | 111 | **5** | 14–23 | **少**（中途用尽） |

同一线程、同一缓冲、尺寸既能偏大也能偏小 ⇒ 不是“前缀声明错了”，也不是残留，
而是**批循环里“本包长度/游标”的算法与缓冲实际内容不一致**：
某些情况下它按上一包/下一包的长度推进，导致本包被截短或被拉长。

下一步最直接的验证：在批循环里记录**每包的起始游标与长度来源**（不是流本身），
即 `sub_1416AB0E0` 里 `0x1416ab789` 之前那段（`sub_140D935E0` 的入参与返回值），
那里应能看出长度是从哪里取的。

### 追加仪器：每次解析前的“缓冲写入次数”（有缺陷，待修）

在入站行里加了一个 `copies` 字段：自上次解析以来，目标为逐包缓冲的 `memmove` 次数
（`detourMemmove` 里计数，解析入口 `exchange(0)`）。

首轮结果（952 行）：`copies=1` 712 行、`copies=0` 240 行。但**这个计数目前不可用**：
上下行共用同一个 `exchange(0)`，中间夹一个上行（144）解析就会把下行刚累积的计数清掉，
所以 `copies=0` 的行里既有“上行包”，也有“被上行清掉”的下行包 —— 无法据此判断
“失败包是否根本没有被填充”。

修法（下一轮第一步，两行）：只在**同一个缓冲地址**的连续解析之间清零；
即记住上次的 `begin`，地址变化时不清零。

## 25. copies 计数：修正后仍不可用；CRT 拷贝钩子会弄死管道（2026-11-01 15:2x）

### 按缓冲地址分槽的计数（已实现）

`noteCopy(dst)` 按地址 4 槽登记、解析时 `takeCopies(begin)` 只取该缓冲的计数并清零。
结果（842 行）：`copies=1` 与 `copies=0` 混合，且**整整几个 tick 全是 0**：

```
tick 60  39/17 → 111/22 → 111/14 …（全部 copies=0，同一缓冲地址）
tick 63  111/21 copies=1
```

同一缓冲、连续解析、全部 0 ⇒ **填充并不走 memmove**（多半走 memcpy 或被内联）。
所以“用 memmove 计数判断是否被填充”这个前提本身不成立。

### 补上 memcpy 后：管道再次死亡

给 `memcpy` 装同款探针后，与之前 memmove 一样**管道立刻失效**（进程仍在、无 crash dump），
两次复现。结论：**在 CRT 拷贝原语上装钩子不可靠**（即使有重入保护），这条路放弃。

### 改用更窄的落点（下一步）

DR 写断点已经给出真正的写入者：`0x140d7d707`（`mov [rdi+0x10], rbx`，在
`sub_140D7D470` 内，`rdi` 就是逐包 string 对象）。下一步应钩**这个游戏函数**并按
`a1 == net_ctx+0x128` 过滤，在调用后读 `[a1+0x10]` 得到“这次写入的 size”，
与解析时看到的 size 直接对比 —— 不碰 CRT，热路径影响也小得多。

需要一次 plumbing：把这个函数地址作为新的角色（`@client_packet_string_assign`）
传进 `violation_watch`（现有 `loop_addr` 已示范了这条路）。

## 26. 赋值钩子落地 + 一个必须记住的坑：`*a1` 是**方向相关**的（2026-11-01 15:4x）

### 新钩子

按 §25 的建议加了 `@client_packet_string_assign = 0x140D7D470` 的 3 参 typed 钩子
（返回 `__int64` 原样转发），调用后若 `target == net_ctx+0x128` 就读取 `[target+0x10]`，
作为该包“写入者给出的 size”，随每条入站行输出 `assign_size`。

现场：`assign_hooked=true`、**`assign_calls=2567`**、`assign_count=0`。

### 为什么 0：`net_ctx` 抓到的是**另一个方向**的对象

同一 run 里读 `net_ctx+0x128` 指向的内容：

```
ns+0x128 -> 数据指针 -> 90 01 00 00 …   （id 144 PlayerAuthInput）
ns+0x138 = 0x5f = 95                    （正是 144 的切片长度）
```

即这次 `*a1` 是**上行**（144）那个对象，不是下行。之前几轮里 `ns+0x138` 读到的是下行包的
size（如 0x0e/0x17），说明 `*a1` 具体是哪个方向的对象**取决于哪个方向先命中**，
每个进程实例都可能不同。

⇒ 这条解释直接推翻了两处此前的隐含假设：

1. §21 里“DR 命中在 ns+0x138 上 ⇒ 抓到下行写入者”只在该实例里成立；
   这次同址命中的是**上行**字符串的写入；
2. §23/§24 里拿 `net_ctx+0x138` 的写入 tid 与下行解析 tid 比较，**方向可能不一致**，
   所以“同线程、无竞态”的结论需要方向确认后才算数
   （那次两边都是 23848，但两个方向是否同线程仍需分别测）。

### 正确的做法（下一步）

`net_ctx` 只应作为“某个方向的对象”；要覆盖两个方向，需要：
(a) 在解析入口按**该包的 id 所属方向**分别记录两个对象的地址（下行可达 `sub_1416AB0E0`，
上行走另一条链）；或
(b) 直接按**字符串内容首字节**（0x90 01 = 144 = 上行；6f/bb/bc = 下行）给 `net_ctx` 分类，
让 `assign_size` 只在方向匹配时比较。

在此之前，`assign_size` 这个字段不能用来判定任何结论。

## 27. 方向分类落地；赋值钩子仍未命中（2026-11-01 15:5x）

### 已修：只锁定下行上下文

`detourLoopEntry` 改为：取 `*a1` 后读该对象的 string 数据指针，若首两字节是 `90 01`

现场核对：`net_ctx` 对应缓冲首字节 `6f 07 01`（111），确认锁定的是下行对象。

### 但仍未命中

在**下行**字符串（`net_ctx+0x138`）上重新装 DR 写断点，命中的 RIP **仍是 `0x140d7d70b`**
（函数 `0x140D7D470` 内），tid 与下行解析同一线程。可是同一时刻：

```

assign_count = 0      （从来没有一调用满足 target == net_ctx+0x128）
```

1. 该函数的第一参数不是 string（rdi 由别的参数/寄存器推出来），我们的 3 参透传拿到的是别的值；
2. 执行 `0x140d7d70b` 的那份代码与 `0x140D7D470` 不是同一入口（例如热路径用的是另一份实例）。

**本轮未能完成这一步**：IDA 侧会话再次失效（`idb_open reply lost`），重新打开需要数分钟，

## 28. 赋值仪器打通了，但热路径 `readMemory` 会把进程挂死（2026-11-01 15:5x）

### 打通过程（两次纠错）

1. **方向**：`detourLoopEntry` 按缓冲首字节分类（`90 01`=上行，其余下行），只锁下行对象。
   现场核对：缓冲首字节 `6f 07 01`（111）✓。
2. **参数位置**：从磁盘 exe 直接反汇编序言（绕过失效的 IDA 会话）：

```
0x140d7d470  push rbp / push r15 / push r14 / push rsi / push rdi / push rbx
0x140d7d478  sub rsp, 0x68
0x140d7d489  mov rsi, r8
0x140d7d48c  mov rdi, rdx     ← string 在**第二个参数**
0x140d7d48f  mov rbx, rcx
```

之前一直过滤的是第一个参数，所以 0/2567 命中。改成 `a2` 后：**matched 1285 / calls 2510**。

### 正常流量下的对照（关键基线）

按缓冲地址分槽存放 assign 写入的 size，与解析时的 `packet_size` 对比：

| 结果 | 数量 |
| --- | --- |
| 相等（全部下行包） | **897** |
| 不等 | 127（全部是上行 144，未挂钩，assign 记 0） |

即：**正常时，解析看到的 size 恰好就是写入者写下的 size**（下行 897/897 一致）。
这让失败样本的判定变得干净：只要拿到一次失败，比较这两个数即可。

### 但复现循环第 1 次就把管道挂死

修法（下一步，明确）：热路径**不做任何 `readMemory`**——只把 string 指针和一个序号写入
预分配槽，size 的读取放到管道线程的 drain 里做（那时锁已释放，且对象仍有效或可判失效）。

### 状态

- 仪器逻辑已验证（下行 897/897 一致），但**不能在 flight 场景长时间运行**；
- 因此仍未取得“失败样本的 assign_size vs packet_size”这一对数；
- 五次历史样本（36/23/8/5）的成因仍未定。

## 29. 定案的一半：解析 size 就是写入者 size，长度来自更上游（2026-11-01 15:5x）

### 仪器修好

热路径不再调用 `readMemory`（那是挂死原因）：循环钩子只在**尚未锁定时**分类一次、
之后零访存；赋值钩子改用直接读（对象已按地址校验过）。整轮 flight 存活，
`assign_calls 6414 / matched 3612`。

### 失败样本（`pb20-5`，tick 1842）

完整错误文本第一次拿到（context 上限放宽后不再截断）：

```
BinaryStream read() overflow checkedNumber = 10, mReadPointer = 2,
buffer Length is = 2 bytes
readNoHeader failed! packetId: 187
```

同 tick 的入站行（含新字段）：

```
1842  id 187  size 2   assign 2   copies 0   hex bb01
1842  id 156  size 136 assign 0   hex 9c010004f6028001 42696e61727953…
```

### 判定

1. `[实测]` 该包 **写入者写入 2 字节**（`assign_size = 2`），**解析也读到 2 字节**
   （`packet_size = 2`，错误文本里 `buffer Length is = 2 bytes`）。三者一致。
2. `[实测]` 正常基线是 897/897 一致（§28），所以这不是读数误差。
3. ⇒ **长度不是解析侧产生的，也不是解析缓冲残留**：187 的帧在上游就被做成了 2 字节
   （只有 id varint `bb 01`、没有 payload），写入者原样搬过来，解析器按 187 的 schema 要 10 字节
   → overflow（error 29）→ `BadPacket(90)`。
4. 这一条**支持“上游按声明长度切出 2 字节”**（模型 A），并**否定“解析缓冲残留”**（模型 B）：
   残留只会让字节变多，不会让写入者写 2。

### 随后那条 136 字节“id 156”

`9c 01 00 04 f6 02 80 01` 之后就是 ASCII `BinarySt…` —— 正是刚生成的错误文本。
`[推断]` 连接已在拆除，批缓冲被释放/复用，越界的那次解析读到了堆上刚建的字符串；
属于**失败后的连带现象**，不再作为判据（此前 §24 那个“1 字节包”同理）。

### 结论更新

- 失败帧的长度**在组帧/切分层就已经是错的**（2 而不是 35），与解析器无关；
- “复用缓冲残留”在本样本上被否定；
- 剩下要定的只有：**上游是谁把这个帧做成 2 字节的**（长度前缀读错、还是切分游标错位）。
  这已经不在解析链里，需要回到 `sub_140D935E0` 之前的那一层。

## 30. 上游钩子不可行：`sub_1416C6070` 直接杀死进程（2026-11-01 16:2x）

按计划在 `sub_140D935E0` 之前那一层加探针，逐个试了三种落点，全部失败：

| 落点 | 结果 |
| --- | --- |
| `memmove` / `memcpy`（CRT） | 管道失效（进程存活、无 dump），去掉热路径 `readMemory` 后**仍然** |
| `sub_140D7D470`（string 赋值） | **可用**：6414 调用 / 3612 命中，整轮 flight 存活 |
| `sub_1416C6070`（赋值之上那层指派） | **进程直接退出**（pipe 关闭，`ModDisconnected`） |

结论：**这个 harness 只能安全钩同一条解析链里的“游戏自己的函数”**（解析循环、赋值函数）；
CRT 拷贝原语与更上层的指派函数都会把进程搞坏。`sub_1416C6070` 的 ABI 很可能不是
`(void*, void*) → __int64`（我们的透传参数或返回值破坏了调用方）。

### 这一层的可观测边界（记录）

- 已经能稳定观测：入站切片（id/大小/字节）、`assign_size`（写入者写的 size）、
  DR 写断点（写入指令 + 线程）、解析错误全文。
- 已经证明：**解析看到的 size == 写入者写的 size**（正常 897/897，失败样本 2/2/2），
  长度在赋值之前就已确定；残留模型被否。
- 不能观测：赋值函数的**入参长度**（a1/a3 都不是长度/源，实测记到的是指针），
  以及更上层的切分决策。要拿到它需要能安全钩住调用链更上层，目前做不到。

### 结论归档

- 现象层：入站帧长度错误（2 / 8 / 23 / 36 等，围绕该包正常大小浮动）→ 解析失败 →
  `BadPacket(90)`。
- 责任层：**在游戏的入站组帧/切分路径**，位于 `sub_140D935E0` 之前；mod 不写这些数据。
- 未闭合的部分：具体是哪个函数、哪一步决定这个错误长度。原因不是证据缺失，
  而是**观测手段受限**：任何比“赋值函数”更上游的钩子都会破坏进程。
- 附带结论：这也说明 **mod 的 hook 会显著影响进程稳定性**，因此“完全排除 mod 影响”
  仍未成立（与 §16 的保留一致）。

```
0x1416ab32d  call memcpy                 ; 拷一个 0xB0 的包对象
0x1416ab332  mov  r12, [rsi+0xa0]        ; 遍历 handler 向量
0x1416ab359  mov  rcx, [r12]             ; 元素 = 指针
0x1416ab35d  mov  eax, [rcx+0xa8]        ; 元素上的 id/类型
0x1416ab363  cmp  eax, [rbp+0x78]        ; 与当前包的目标值比较
0x1416ab36b  call sub_140D95C80          ; 命中后进一步判断
```

### 得到的结论

1. `[代码]` 这个循环遍历的是**handler/包对象向量**（`[rsi+0xa0]`，8 字节元素，元素再指向带 `+0xa8` 字段的对象），
   **不是字节缓冲**；循环里没有 varint 解码、没有切片计算。
2. `[代码]` 传给 `sub_140D935E0` 的 `a2` 就是 `&(rsi+0x128)`——
   结合 §19/§31 的上一条：`sub_140D935E0` 用 `a2->data`、`a2->size` 建解析流。
3. ⇒ **长度不是在这条解析链里算出来的**：链上只是“把 `rsi+0x128` 这个 string 的内容包成流”。
   这个 string 的 size 由**拥有 `rsi` 的那一层**（网络/传输侧）设置，写在这两个函数之外。
4. 这与 §29 的实测完全一致：解析看到的 size == 赋值写入的 size（2/2/2），
   而两者都来自那个 string 的 size —— 它的值在进入解析链之前就已确定。

### 因此本调查能给出的最远结论

- 现象：入站帧长度错误（2/8/23/36，围绕该包正常大小浮动）→ 解析失败 → `BadPacket(90)`。
- 责任层：**网络接收/组帧层**，在 `sub_1416AB0E0` 之外（设置 `rsi+0x128` 这个 string 的 size 的地方）。
- 解析链（`sub_1416AB0E0` → `sub_140D935E0` → string 赋值 → `Packet::readNoHeader`）已完整映射，
  它不是产生错误长度的地方。
- 再往上不可达的原因（已实测）：CRT 拷贝钩子会让管道失效，`sub_1416C6070` 会让进程退出。
  ⇒ 要闭合到具体函数，需要换观测手段（例如外部调试器/ETW），而不是继续在本 mod 里加钩子。

### 交接补充：`net_ctx` 对象的形态

现场读 `net_ctx` 前 0x18 字节，是**三个连续 vptr**（多继承布局）：

```
net_ctx+0x00 -> 静态 0x14e75e2f0
net_ctx+0x08 -> 静态 0x14e75e330
net_ctx+0x10 -> 静态 0x14e75e360
```

离线扫了这三个 vtable 各 24 个槽、每槽前 ~500 条指令，**没有**任何一个槽直接写 `+0x138`，
说明“设置包长度”不是这些虚函数直接做的（可能经非虚成员或更深一层的 helper）。

### 交接：下一步能闭合的做法（不需要再加 mod 钩子）

1. 用**外部调试器**（x64dbg/WinDbg）对 `net_ctx+0x138` 下硬件写断点，拿完整调用栈——
   这正是本 mod 做不到的（进程内钩子会破坏调用方），但外部调试器不受此限；
2. 或对该对象的 `+0x128` string 做 **ETW/内存写监视**；
3. 拿到写入函数后，回到 IDA 反编译它，看长度是**从帧头 varint 读的**还是**按缓冲大小算的**——
   这一步将最终区分“声明长度错”与“缓冲长度错”。

本仓库侧的证据已足够支撑到这个交接点：解析链完整、长度来源定位到“进入解析链之前的 string size”，
且已证明解析器忠实使用了那个值。

## 34. 赋值调用者与参数实测（2026-11-01 17:3x）

用 `_ReturnAddress()` 在赋值钩子里直接取调用者（零访存），再逐个记录寄存器参数。

### 结果（`[实测]`）

| 量 | 值 |
| --- | --- |
| 调用者（静态） | **`0x1416c608d`** —— `sub_1416C6070` 里 `call [rip+0xda35a1b]` 的下一条，逐个包都相同 |
| `a1`(rcx) | 常数指针，逐包不变 |
| `a2`(rdx) | 常数指针 = `net_ctx+0x128`（我们过滤用的目标 string） |
| `a3`(r8) | 常数指针，逐包不变 |
| 写入的 size | 21 / 17 / 14 / 22 …（逐包变化，与解析一致） |

现场再读该对象的字段：`[a2+0x10]` = `0x16` = 22，正是当时那个包的长度；
`[a2+0]` 是指向包字节的指针。⇒ **a2 就是那个逐包 string，size 写在 +0x10**。

### 结论

1. `[实测]` 三个寄存器参数**都不是长度**（全是逐包不变的指针），长度是赋值函数**内部**算出来的；
2. `[代码]` `sub_1416C6070` 的调用点固定：`mov rcx,[rcx+8]; mov rax,[rcx]; mov rax,[rax+0x40];
   call [rip+…]`，返回地址 `0x1416c608d`，与逐包观测一致；
3. 赋值函数内部：`mov rdi,rdx`（目标 string）、`mov rbx,rcx`、`mov rsi,r8`，
   之后 `mov [rdi+0x10], rbx` 写 size、`memmove(dst, r9, rbx)` 拷贝 ——
   **计数 `rbx` 与源 `r9` 都由函数内部推出**，我们的三参透传看不到 `r9`。

### 下一步（精确）

把赋值钩子扩到**四参**（rcx/rdx/r8/r9），记录 `r9`；再在 drain 里读 `[r9+0x10]`。
若 `[r9+0x10]` 等于写入的 size，则长度就是**源 string 的 size**——
那就回到“谁把源 string 设成 23 字节”，仍是组帧层那一问；
若不等，则计数由别的字段/参数决定，需要再拆 `sub_140D7D470` 的内部路径。

### 四参实测：`r9` 也不是源（2026-11-01 17:4x）

把赋值钩子扩到四参并记录 `r9`：

```
size 22  r9 0x52c        r9_size None
size 17  r9 0x5fd        r9_size None
size 21  r9 0x7ffed000   r9_size 0
size 23  r9 0x7ffed000   r9_size 0
```

`r9` 逐包变化但是**小整数/栈样值**（0x52c、0x5fd、0x7ffed000），不是源 string 指针，
也不是长度本身。⇒ 记账函数（`sub_140D7D470`）的长度与源都**只在函数内部**确定，
寄存器入口一个都不带。

### 到此为止能确定的（本线程）

- 调用链固定：`sub_1416AB0E0`（解析循环）→ `sub_140D935E0` → `sub_1416C6070`
  （`0x1416c6087` 间接调用）→ `sub_140D7D470`（写 `[string+0x10]` 的 size，
  随后 `memmove`）；
- 长度不是任何入口参数，是 `sub_140D7D470` 内部算的；
- 该值最终等于解析器看到的 size（正常 897/897，失败样本 2/2/2）。

要继续只能**逐路径拆 `sub_140D7D470`**（0x323 字节、多分支），把写 size 的那条路径
（`0x140d7d707` 之前）的计数来源读清楚——这属于纯静态工作，不再需要新探针。

### 静态读 `sub_140D7D470` 的写 size 路径（`[代码]`，2026-11-01 17:5x）

函数前段是 **profiler 计时**（`Query_perf_frequency/counter` + 纳秒换算），
真正干活的部分在 `0x140d7d635` 之后：

```
0x140d7d635  movups xmm0, [r15]          ; 取一个元素
0x140d7d639  movups xmm1, [r15+0x10]
0x140d7d63e  movaps [rbp-0x20], xmm1
0x140d7d642  movaps [rbp-0x30], xmm0
0x140d7d646  mov qword [r15+0x10], 0     ; 该元素 size = 0
0x140d7d64e  mov qword [r15+0x18], 0xf   ; capacity = 15
0x140d7d656  mov byte  [r15], 0
0x140d7d65a  mov rax, [r15+0x20]
...
0x140d7d6b4  inc rbx                     ; ← 计数递增
...
0x140d7d707  mov [rdi+0x10], rbx         ; ← 写目标 string 的 size
0x140d7d714  call memmove                ; 再从 r9 拷 rbx 字节
```

观察（`[推断]`，未定案）：这条路径在**遍历一个容器**（`r15` 每次前进、把元素 string 清空），
`rbx` 随之 `inc`，最后被当作 size 写出去并交给 `memmove`。
这更像“**元素个数**”而不是“字节数”。若成立，失败样本里 2 / 8 / 23 / 36 这类值
就是容器元素计数（或计数与字节数混用）的产物——但这与“正常 897/897 时 size 恰等于包长”
需要进一步对照才能确认。

下一步：把这条路径的**入口条件**与 `rbx` 初值读清楚（它来自哪个字段/哪个容器长度），
以及它和另一条“按字节拷贝”的路径如何分支。这是纯静态工作。

## 36. 读通 `sub_140D7D470`：它是在**出队环形缓冲**（`[代码]`，2026-11-01 17:5x）

逐条读完整个函数（217 条指令），写 size 的那些指令所在的路径完整如下：

```
0x140d7d5ca  lea  r15, [rbx + rbx*4]        ; r15 = rbx*5
0x140d7d5ce  shl  r15, 3                    ; r15 = rbx*40 (0x28)   ← 元素大小
0x140d7d5d2  add  r15, [r14 + 0x88]         ; r15 = 环底 + 索引*0x28
0x140d7d5d9  lea  rax, [rbp - 0x30]
0x140d7d5dd  cmp  rax, r15
0x140d7d5e0  je   0x140d7d65a                ; 同一对象则跳过搬移
0x140d7d635  movups xmm0, [r15]              ; 元素里的 std::string
0x140d7d639  movups xmm1, [r15 + 0x10]
0x140d7d63e  movaps [rbp - 0x20], xmm1       ; ← size / capacity 落到局部
0x140d7d642  movaps [rbp - 0x30], xmm0       ; ← 数据指针落到局部
0x140d7d646  mov qword [r15 + 0x10], 0       ; 清空该元素的 size
0x140d7d64e  mov qword [r15 + 0x18], 0xf     ; capacity=15
0x140d7d656  mov byte  [r15], 0
0x140d7d65a  mov rax, [r15 + 0x20]           ; 元素第 0x20 字节里的附加字段
0x140d7d65e  mov [rbp - 0x10], rax
...
0x140d7d6b4  inc  rbx                         ; ← 环索引 +1
0x140d7d6b7  and  rbx, [r14 + 0x90]           ; ← 与掩码相与（环形回绕）
0x140d7d6be  mov  [r14], rbx                  ; 写回索引
0x140d7d6c1  mov  rbx, [rbp - 0x20]           ; rbx = 刚搬出来那个元素的 size
0x140d7d6c5  test rbx, rbx
0x140d7d6c8  je   0x140d7d6f4                  ; size==0 走另一分支
0x140d7d6e2  cmp  rbx, [rdi + 0x18]           ; size <= 目标容量?
0x140d7d6e7  call sub_14009DAF0               ; 不够则扩容
0x140d7d707  mov  [rdi + 0x10], rbx           ; ← 目标 string 的 size = 元素 size
0x140d7d714  call memmove                     ; 从元素搬 rbx 字节

```

### 结论（`[代码]`）

1. `sub_140D7D470` **不是“算长度再拷贝”**，而是**从一个环形缓冲出队一个元素**：
   元素 0x28 字节（`std::string` 0x20 + 一个 qword @+0x20），
   环底在 `[r14+0x88]`、索引在 `[r14]`、掩码在 `[r14+0x90]`。
2. 写进解析缓冲的 **size，就是那个元素自己的 `size`**（`[rbp-0x20]` 来自 `[r15+0x10]`）。
3. 因此“长度从哪来”的答案在本层是：**长度是入队方写进环槽的值**，出队只是搬运。

### 与 897/897 基线的关系

正常时每个槽装的就是一个完整包（size = 包长），出队照搬，所以解析看到的 size 恒等于包长；
失败样本的槽 size 是 2 / 8 / 23 / 36 —— 说明**入队那一刻**这个槽的 size 就已经是这个值。

- 它把源 `std::string const&` 的 **`+0x10`（MSVC `_Mysize`）**写进元素 `+0x10`；
  出队再把同一元素搬进解析缓冲。中间没有任何一层改写长度。
- 因此「解析看到的 size」=「入队那一刻源 string 的 `size()`」。

### 静态（`[代码]`，capstone 反汇编 + vtable 槽）

入队 `sub_140D7CFC0(this, std::string const& src)`，快路径写元素：

```
140d7d037  mov r15, qword ptr [rbx + 0x10]     ; r15 = src.size()   (rbx = src)
140d7d03b  cmp qword ptr [rbx + 0x18], 0x10
140d7d040  jb  0x140d7d045
140d7d042  mov rbx, qword ptr [rbx]            ; 堆字符串：取数据指针
...
140d7d2da  mov rdx, qword ptr [r13 + 0x88]     ; node->elements
140d7d2e1  lea rcx, [rcx + rcx*4]              ; rcx = index * 5
140d7d2e5  mov qword ptr [rdx + rcx*8], rdi      ; elem +0x00
140d7d2e9  mov qword ptr [rdx + rcx*8 + 8], r14  ; elem +0x08
140d7d2ee  mov qword ptr [rdx + rcx*8 + 0x10], r15  ; elem +0x10 = SIZE
140d7d2f3  mov qword ptr [rdx + rcx*8 + 0x18], rsi  ; elem +0x18 = capacity
140d7d2f8  mov qword ptr [rdx + rcx*8 + 0x20], rbx  ; elem +0x20 = 时间戳(ns)
```

（`capacity*0x28 + 0xAE`）。

§37 误判的原因：`[rdx + rcx*8 + 0x10]` 里的 `rcx` 不是索引本身，而是
`lea rcx,[rcx+rcx*4]` 之后的 `idx*5`，再乘 8 正好 0x28 —— 与出队
`lea r15,[rbx+rbx*4]; shl r15,3` 是同一个步长。`mov [rax+rcx+0x88], r9`
则是新建节点时写「元素数组指针」（`rax` = 新分配块，`rcx` = 对齐补偿），

### 动态对质（`[实测]`，2026-11-01 18:5x，hook_install va=…cfc0）

### 调用链（`[代码]`）

```
0x140D7CFC0(入队)  ← 0x1416B08C0  ← 0x1416B0490  ← 0x140D809E0 (vtable +0xC0)
```

即：**入队的源 string 是连接对象的序列化缓冲 `conn+0x1b0`**，
`0x1416B0490` 每次都先把它清空（`[str+0x10]=0`、`[str+0x18]≥0x10` 时写 `[str]=0`），

### 完整结论链（修订版）

1. 解析缓冲 = 环元素出队的拷贝（`sub_140D7D470`）；
2. 元素 size 由入队 `sub_140D7CFC0` 写，取值就是源 string 的 `_Mysize`；
3. 源 string 是连接对象的序列化缓冲（`conn+0x1b0`），由 `sub_1416B0490` 清空后交给序列化；
4. ⇒ 失败样本的 2 / 8 / 23 / 36 **就是发送侧序列化出来的长度**；
   环、出队、解析三层都不再改写长度。
   责任面由此从「组帧/队列」收窄到「序列化写入 `conn+0x1b0` 的那一层」。

### 观察到的风险（`[实测]`，未定案）

- 用通用 VA detour hook 入队 6 秒内稳定（0 lost），可以放心做短窗口采样；
- 同一次实验里随后安装 `dispatch_addr=0x1416C6070` 的 hook，进程立刻退出
  （boot log：`violation watch: installed` 之后 `pipe: peek failed`，进程消失）。
  这与早前「`sub_1416C6070` 的 ABI/返回约定不符，不能挂」的结论一致：
  **不要再挂 dispatch**。

## §39 「声明长度」模型退场：这条路上没有帧长度前缀（2026-11-01 19:0x）

复核意见要求「直接读取帧长度前缀，或证明切分函数的数据流」。两条都做了，结论是
**这条路上根本没有帧长度前缀**，因此「声明长度 23」这个提法在本层不成立。

### 1. 入队方的帧格式（`[代码]`）

`sub_1416B0490`（= `NetworkSystem` 的「把包投递给连接」）：

```c
memcpy(Src, a2, 0xB0);                       // 克隆包对象
v8 = alloc(0xB8); memcpy(v8, Src, 0xB0); v8[0xB0] = a4;
for (v9 = 55; v9 != 59; ++v9)                // 55..58 四个观察者槽
    if (a1[v9]) (*a1[v9]->vtbl[0x50])(a1[v9], v41, a3);
v16 = a1[54];  v16[2] = 0;                   // ★ 序列化缓冲 = *(a1+0x1B0)，先清空 size
if (v16[3] >= 0x10) v16 = *v16;
*(u8*)v16 = 0;
v17 = a1[54];  a1[50] = v17; a1[51] = v17[2]; a1[52] = 0;   // a1+0x190 流视图
(*a1[45]->vtbl[0x60])(a1+45, packetId | (a4<<10) | (peer<<12), "Header Data", 0);
(*a3->vtbl[0x28])(a3, a1+45, v21, v22);      // ★ peer 把 payload 追加进去
...
sub_1416B08C0(a1, a2, a3, a1[54]);           // ★ 把 *(a1+0x1B0) 这个 string 广播入队
```

也就是说，一帧 = `varint 包 id`（由 `"Header Data"` 写入）+ `payload`，
**没有任何长度字段**；长度就是这个 `std::string` 自己的 `_Mysize`。

### 2. 切分函数的数据流（`[实测]`，`out/live-inbound-*.jsonl`）

`violation_watch` 的入边记录里 `packet_id` **不是 MC 包 id**，而是「第几个参数带流」
（`record.packetId = argIndex`，见 `publishInbound`）。真正有用的是：

- `parent_view` / `parent_size`：**4444 行里 0 行命中** —— 切片从来不是某个更大流的子区间；
- `before_hex`：多数是 `8e 8e 8e …`（堆填充字节），说明切片就是自己那块分配的开头；
- `error_value` = 进入 `readNoHeader` 时的 `readPtr`：`6f…` 那批恒为 1、`90 01…` 那批恒为 2,
  正好等于包 id varint 的字节宽度 —— 说明调用方先读掉 id 再进 `readNoHeader`。

⇒ 没有「外层缓冲 + 长度前缀 → 切一刀」的结构。切片长度 100% 等于
入队时那个 `std::string` 的长度；`2 / 8 / 23 / 36` 不是被谁声明出来的，
是序列化结果本来就这么长。

### 3. 这改变了结论边界

| 旧说法 | 现状 |
| --- | --- |
| 「帧声明长度 23，实际只有 7」 | **撤回**：本层没有声明长度 |
| 「切片包含额外邻居 payload」 | **撤回**：切片不属于任何更大缓冲（parent_view 恒 0） |
| 「队列/解析可能改写长度」 | **排除**：入队写 `_Mysize`，出队 `memmove(size)`，中间无可改点 |
| 责任面 | 收窄到 **序列化写入 `a1+0x1B0` 的那一层**（`"Header Data"` + `peer->vtbl[0x28]`） |

### 4. 现有失败样本能说明什么

已存样本 `out/diagnostic-full-final-violation.json`：

```
packet_id 39 / packet_size 34 / error_value 104 / response 3
context "BinaryStream read() incomplete.readNoHeader fai…"
```

按本节的模型：这是一个 **34 字节的完整帧**（1 字节 id + 33 字节 payload），
序列化时就是 34 字节；是**包内部的字段读不齐**（`ensureReadCompleted` → 104），
不是外层把帧切短了。

等长时捕获（`out/live_inbound_capture.py`，2 秒一轮落盘）在自然复现时
抓到出事那一帧的 `context_hex`，再逐字段比对一个正常的 id 39 帧，
定位是哪个字段的长度/类型读偏了。

### §40 附二：id 39 payload 的可见结构（`[观察]`，2026-11-01 19:4x）

整帧落盘后能直接看出重复结构。三帧对比（去掉首字节 id `0x27`）：

```
17B : 0f 01 00 07 07 80 80 c0 84 80 83 80 03 | 00 00 00
18B : 01 01 00 07 07 90 80 c0 80 80 82 80 03 | 00 00 95 06
328B: 02 3f 00 07 07 80 80 c0 84 80 80 80 03 | 01 02 02 02 …
```

- 头 3 字节像两个 varint（actor id、tick）加一个 0；
- 紧跟 `07 07` 与 7 个高位字节（`80/c0/84/90/82/83`）像**属性位图**（56 位，按变长压过）；
- 之后 `03` 起是条目流，328 字节帧里的条目呈稳定形状

```

2b 02 02 00              ; 索引 2b / 类型 02 / 02 / 值 0
4d 02 02 00
5c 07 07 80 80 80 20
```

即**「索引 + 类型 + 子类型 + 按类型定宽的值」**的条目序列，类型决定后面吃几个字节。

⇒ 一旦某个条目的**类型字节**在写侧和读侧被解释成不同的宽度，后面整条流就会错位，
最后 `ensureReadCompleted` 报 104。这与「低频、与具体属性内容相关」的现象吻合；
但**具体是哪一个属性 / 哪一种类型**，仍然只能等出错帧落地后再逐条比对。

### §38 附二：入队是**深拷贝**，不与连接缓冲共享（`[代码]`）

有人会怀疑「入队只搬 5 个 qword（指针+长度+容量），源缓冲随后被下一次序列化覆盖」。
读入队函数的前半段可以直接否掉：它对堆上的字符串**另分配再拷**。

```
140d7d04e  cmp r15, 0xf                  ; size <= 15 ?
140d7d052  ja  0x140d7d065
140d7d054  mov rdi, [rbx]                ; SSO：直接取 16 字节内联缓冲
140d7d057  mov r14, [rbx + 8]
140d7d05b  mov esi, 0xf                  ; 容量 15
...
140d7d0ba  lea r14, [rsi + 1]            ; 容量 + 1
140d7d0c1  call [rip + 0x0e37e9e1]       ; operator new
140d7d0d3  lea r8, [r15 + 1]             ; size + 1
140d7d0d7  mov rcx, rdi                  ; dst = 新缓冲
140d7d0da  mov rdx, rbx                  ; src = 源字符串数据
140d7d0dd  call 0x14e5a6390              ; memcpy
140d7d0e2  xor r14d, r14d
```

⇒ 环元素拿到的是**独立副本**；之后连接把 `conn+0x1B0` 清空/重写都不会影响已入队的元素。
「入队后源缓冲被覆盖导致内容与长度不一致」这条猜想**排除**。

### 读取器身份（`[代码]`）

- `0x14357DC30` = `mov eax,0x1D; ret` → **`UpdateAttributesPacket::getId()`**；
  vtable 槽 `0x14E7C1B08`，name 槽 `0x14E7C1B10`（`0x14357DC40`）；

1. 这 6 字节是**另一个包（UpdateAttributes）残留的前缀**，真正的包（187）从 **offset 6** 开始；

4. 同样的错位在另一个时刻会让**真正的包**（187）读完后还剩尾巴 → `read() incomplete`，

## §48 抓到「粘连帧」的生产栈（2026-11-01 23:36）

- 前 7 字节 `bc 01 00 00 00 00 01` 是**一个完整的 188 帧**（正常 188 就是 7 字节）；

⇒ 解析器在同一块 55 字节缓冲上先读掉 188（7 字节），再按 187 读，读不完 → 104。
这就是 2026-11-01 22:20:40 那次失败的**同一形状**，只是这次粘连的前缀是 188 而不是

### 生产栈（`[代码]`）

| 帧 | 地址 | 归属 |
| --- | --- | --- |
| 0 | `0x1416B080A` | `sub_1416B0490` 内（清空缓冲 → 写 Header Data → peer 写 body → 入队） |
| 1 | `0x14103F226` | `sub_14103EDB0` |
| 2 | `0x141A1D97A` | `sub_141A1D810` |
| 3 | `0x14901C0C7` | `sub_14901BD20` |
| 4 | `0x1463CC2E5` | `sub_1463CC280` |

⇒ 粘连不是解析侧造成的，也不是队列造成的：**它是在 `sub_1416B0490` 这条"共享
序列化缓冲"路径内部产生的**。该路径每次都会清空 `netSystem+0x1B0` 并把流视图

1. **两个线程同时对同一个 `netSystem` 调用这条路径**（缓冲与流视图都不是线程安全的），
   清空与写入交错；
2. 清空之后、写 header 之前，另一个写者已经把 7 字节写了进去，随后的 body 接着往后写。

两种都指向同一个结论：**共享的序列化缓冲缺少串行化**。


三条独立事实：

1. **两个 tid（42212 / 12404）在同一个 tick 交替使用同一个 `netSystem` 的缓冲**；
2. `before/after` 链条自相矛盾（`0→19`、`19→15`、`2→54`、`15→54`、`54→21`），
   不是单线程串行的形状；
3. `2 → 54`、`15 → 54` 两次都产出 **54 字节**的帧，而同一 tick 入队侧抓到的
   54 字节帧头部是 `6f 0e 01 …`（id 111）。

紧接着（tick 311）回调：

```
packet_id 111  packet_size 54  error_value 104  response 3
"BinaryStream read() incomplete.readNoHeader failed! packetId: 111"
```

⇒ **解析器读到的就是这个粘连帧**：`6f 0e 01` 之后跟的是另一个包的内容，
`ensureReadCompleted` 失败 → 104 → BadPacket(90) → 断线。

### 结论

`[实测]`+`[代码]`：每个 `NetworkSystem` 只有**一份**序列化缓冲
（`+0x1B0` 的 `std::string` 与 `+0x190..+0x1A0` 的流视图），`sub_1416B0490`
在写之前清空它，但**两个线程会同时走这条路径**（本轮实测 tid 42212 / 12404）。
清空与写入交错，于是：

- 一个包的内容被写到另一个包前面（§47 的 `1d 01 … + 187`）或后面（§48 的 `188 + 187 尾巴`），
- 粘连帧被解析器当成"第一个包"，剩下的字节触发 104 / 或让下一个 id 读成垃圾（§47 的 29 + 14718）。

三条现场（22:59 的 187/29、23:36 的 188+187、00:0x 的 111/54）**同一机制**。

### 这不是 mod 造成的

两处探针都只读：入队探针读目标字符串的 `_Mysize` 与首字节，序列化探针读
`[netSystem+0x1B0]`→`_Mysize`；没有任何写。并发的一对 tid 在探针之外也存在
（§42 无 hook 对照里世界同样会丢，只是当时没有记录手段）。

### 最小修复的方向（不在本仓库）

这是游戏侧共享缓冲缺少串行化，**不应由 harness 去打补丁**。可行方向只有两条，
都需要上游（或服务端侧）改动：

1. 每个发送方各自持有序列化缓冲（把 `+0x1B0` 挪到连接/线程局部）；
2. 或在 `sub_1416B0490` 的"清空→写 header→写 body→入队"整段加锁。

harness 侧能做的只是**规避**：避免在服务端 tick 外并发触发发包
（例如飞行/能力改动的注入节奏），以及把这条结论作为已知限制记录下来。
