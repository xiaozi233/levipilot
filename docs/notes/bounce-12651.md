## 1. 术语

| 记号 | 含义 |
| --- | --- |
| `preY` | 落地 tick 的移动前 AABB 下界（脚底） |
| `δy` | 该 tick 的**请求**竖直位移（负 = 向下），含重力与阻力 |
| `top` | 覆盖块碰撞形状的上表面；与黏液顶重合时 `top = slimeTop + h` |
| 探针 | `脚底 − 0.2`（解析器把查询盒的 Y 压成这个平面，X/Z 仍是脚底范围） |
| 形状 | 一条世界空间 AABB，6 个 float / 24 B（minX,minY,minZ,maxX,maxY,maxZ） |
| 中心 | 形状的竖直中心 `(minY + maxY) / 2` |
| 候选表 | `MoveRequest+0x58` 的 `vector<AABB>`；`+0x70` 是对应的方块指针 |
| 收集盒 | 决定「哪些方块进候选表」的并集盒，§3.3 |

## 2. 判定链

一个 tick 内三段，按执行顺序。

### 2.1 触发 `[代码]`

`@bounce_handler = 0x148B5DB00`，逐实体执行；条件 `(flag & 2) == 0` 且
`vy < 0 && |vy| ≥ 0.080000117f`（`@bounce_threshold_f32 = 0x14EA350B0`）。

```c
if ((*flag & 2) == 0) {
  vy = state_vector.vel.y;                     // StateVectorComponent, [r8+0x1C]
  if (vy < 0 && fabsf(vy) >= 0.080000117f) {
    aabb_copy = *aabb;                         // AABBShapeComponent, 24 B，移动后
    resolver(container, &out, &aabb_copy);     // container = MoveRequest + 0x58
    ...
```

### 2.2 选块 `[代码]`

`@block_pos_resolver = 0x141E144A0`：

```c
v = aabb[1] - 0.2f;                 // 探针
aabb[1] = v; aabb[4] = v;           // 查询盒 Y 压成平面，X/Z 不变
for (shape : shapes) {              // 24 B/个
  cy = (shape.maxY - shape.minY) * 0.5f + shape.minY;
  if (v - cy < 0) continue;                         // 中心高于探针 → 跳过
  if (v - cy < best_d) { best = shape; best_d = v - cy; }   // 取最高中心
  else if (v - cy == best_d) { 水平中心更近者优先 }
}
if (best) { pos = floor(shape.min); block = refs[best_index]; }
```

三处容易读错的地方：

1. 探针是**一条水平面**，不是点；判定是「形状中心的**高度** ≤ 探针」，不是「点落在方块里」。
2. 中心是**碰撞形状**的中心，不是方块中心。3 层雪形状 `[−59, −58.625]` → 中心 `−58.8125`；
   同一格的整块方块中心在 `−58.5`，比雪面还高 0.125，两者差 0.3125。
3. X/Z 中心只在「两个形状到探针距离完全相等」时用来决平，不参与主判定。

### 2.3 结算 `[代码]`

选中方块经 vtable `+0x3E8` 取 restitution `coef`；`|coef| > 1.1920929e-7` 时写
`ApplyRestitutionComponent(0x7DF54114).y = max(coef × −vy, 当前值)`。
`coef == −1` 且已有正值时走蜂蜜粘性分支（清零 y，必要时触发旁的逻辑）。

### 2.4 覆盖高度阈值

脚落在覆盖块顶，探针 `= top − 0.2`；覆盖块中心 `= top − h/2`。
覆盖块被选中 ⇔ `top − h/2 ≤ top − 0.2` ⇔ **`h ≥ 0.4`**。
`0.4` 不是任何常量：它是 `[代码]` 的探针判据除以 `[实测]` 的形状高度得到的推导值。

| `h` | 例子 | 覆盖块被选中 | 结果 | 证据 |
| --- | --- | --- | --- | --- |
| 0.0625 | 地毯 | 否 | 弹 | 推断（同公式） |
| 0.125 | 雪 1 层 | 否 | 弹 | 实测 0.25–6.0；模型在 0.25–12 上无缝隙（§4 已验证） |
| 0.1875 | 打开的地板门 | 否 | 弹 | 推断 |
| 0.25 | 雪 2 层 | 否 | 弹，但有 8 个 1/16 宽的窄缝（§4） | 实测 |
| 0.375 | 雪 3 层 | 否（中心只高 0.0125） | **随落地相位翻转** | 实测 + `[代码]` |
| 0.4375 | 原版无此高度 | 是 | 不弹 | 公式 |
| 0.5 | 雪 4 层 / 下半砖 | 是 | 不弹 | 雪实测；半砖推断 |
| 1.0 | 整格 | 是 | 不弹 | 推断 |

「不弹」的前提是覆盖块自身 restitution = 0（雪、砖都满足）；上面再叠一块黏液块时
`h = 1` 也会弹。为什么 `0.375` 是**唯一密集翻转**的高度：缝隙条件是
`min(preY − 0.5681, preY + δy − 0.2) ≥ slimeTop`，而 `slimeTop = top − h`——覆盖越厚，
门槛越低，缝隙越容易成立（薄覆盖要求落地 tick 的脚底已经离顶面很近）。2 层也有同源
窄缝，只是稀得多（§4）。

## 3. 候选表

### 3.1 宿主与内存布局 `[代码]` + `[实测]`

宿主是 `MoveRequestComponent`（id `0x4C8F7288`，152 B）；视图构造
`@move_request_view_builder = 0x148B6AB80`，视图 = StateVector(36) / AABBShape(32) /
MoveRequest(152) / ActorDataFlag(24) / VerticalCollisionFlag。客户端与服务端各持一份，
内容同构。

在 resolver 入口按 `hook_install(mem_arg=0, mem_offset=-0x58, mem_size=128)` 抓 128 B：

| 偏移 | 内容 |
| --- | --- |
| `+0x00..+0x14` | 移动前 AABB（`minY` = 脚底，身高 1.8） |
| `+0x18..+0x2C` | 收集盒（并集盒的缓存；解析器不读它，它只决定「谁进表」） |
| `+0x30..+0x38` | 请求位移，竖直分量在 `+0x34` |
| `+0x3C..+0x44` | 填充读的是这一份 δ；**移动后会被改写成实际应用的（裁剪过的）位移** |
| `+0x48..+0x50` | 0.01, 0.01, 0.01 |
| `+0x58 / +0x70` | 候选形状（24 B/个）/ 方块指针（8 B/个） |

`+0x30` 与 `+0x3C` 在填充时刻相同，移动之后 `+0x3C` 才是裁剪值（实测 3.0 落差：
`+0x34 = −0.6517`，`+0x40 = −0.3054` = 脚到雪面的实际距离）。代价见 E4。

### 3.2 填充代码 `[代码]`

`@collision_gather_runner = 0x1431DC500` → `@collision_gather_system = 0x1431DD080`
（视图 = `{0xAF9E0C56, AABBShapeComponent, 0x9AB0D3FF, MoveRequestComponent}`，前两个 id
未解析出名字）→ `@collision_shape_gather = 0x1431C2F50`（约 900 行，含去重/合并）。

| 地址 | 作用 |
| --- | --- |
| `0x1431C3049`..`0x1431C3122` | 用 `preAABB` 与 δ 做**扫掠盒**（逐轴按符号单向外扩，长度先夹到 16） |
| `0x1431C314A` → `0x14B177650` | **台阶盒**：`*a3 * 1.01`，下扩 `autoStep×1.01`、上扩 `autoStep` |
| `0x1431C3193` → `0x149026EB0` | 第二个候选盒（同样由 δ、autoStep、preAABB 生成） |
| `0x1431C31F7` | 下界再取 `preAABB.minY − 0.2 − |δ.y|` |
| `0x1431C31FC` | 上界再取 `preAABB.maxY + 0.08` |
| `0x1431C324A`..`0x1431C32B0` | 新盒被 `+0x18` 的旧盒**包含**则 `return`（不重建、不改表） |
| `0x1431C34D9` | 重建路径：`a10->vfn[+0xB0](out, &box, 1, …)` 按盒向方块源要形状 |
| `0x1431C34DF` / `0x1431C35FA` | 写回 `+0x58`（`add [r13+0x60], 0x18` 就是 24 B 的 `push_back`） |

### 3.3 盒的化简 `[代码]`

三个盒取并：扫掠盒下界 `preY + δy`、台阶盒 `preY − 0.5625×1.01`、预测项
`preY − 0.2 − |δy|`。`δy < 0` 时第一项恒被第三项盖住，所以

```text
bottom = min(preY − 0.5681, preY + δy − 0.2)
top    = preY + 1.8 + 0.5625          // 台阶盒上扩；+0.08 的上界项被它盖住
X/Z    = preAABB 的 X/Z（水平不扩）
```

`preY` = 移动前脚底，`δy` = 请求位移的竖直分量。

### 3.4 缓存语义

`+0x18` 保存的是最近一次「未被包含」的盒。新盒被旧盒包含时函数直接返回，候选表保持上一次
的内容——所以「表」对应的盒可能比当 tick 的并集盒更宽松。下落过程中盒底持续下移，落地 tick
通常都会重建；从下方接近或上升时才会走到不重建的分支（本轮未测）。

## 4. 落差依赖与预测器

把 §3.3 的盒判据接上竖直积分，就不需要开游戏扫描。本 build 的积分是

```text
v0 = 0 ;  v_{k+1} = 0.98 · v_k + 0.0784        （0.0784 = 0.08 × 0.98）
y_{k+1} = y_k − v_{k+1}
```

落地那一 tick（`y_k − v_{k+1} ≤ top`）给出 `preY = y_k`、`δy = −v_{k+1}`。仓库里的可执行
版本是 [`../../driver/bounce_predict.py`](../../driver/bounce_predict.py)：

```bash
py -3.11 driver/bounce_predict.py --layers 3 --drops 0.5,0.75,1.25,3.0
py -3.11 driver/bounce_predict.py --table        # 各层覆盖的「不弹」落差
py -3.11 driver/bounce_predict.py --validate     # 回放账本里的 60 行实测
```

```python
def predict(cover_top, drop, slime_top=-59.0, auto_step=0.5625):
    y, v = cover_top + drop, 0.0
    while True:                                   # 落地 tick
        v = 0.98 * v + 0.0784
        if y - v <= cover_top:
            dy, feet = -v, cover_top
            break
        y -= v
    box_lo = min(y - auto_step * 1.01, y + dy - 0.2)
    h = cover_top - slime_top                    # 覆盖块高度（底面贴黏液顶）
    probe = feet - 0.2
    if cover_top - h / 2 <= probe:                # 覆盖块被选中 → restitution 0
        return False
    return box_lo < slime_top and (slime_top - 0.5) <= probe
```

对质（先用公式算，再跑）：

| 组 | 样本 | `preY`/`δy` | 候选表 | 弹否 |
| --- | --- | --- | --- | --- |
| L3，0.5–3.5 步长 1/8 | 25 | 25/25 | 25/25 | 25/25 |
| L3，0.5625–2.8125 隔 0.25 | 20 | 20/20 | 20/20 | 20/20 |
| L2，15 档含 1/16 细档 | 15 | 15/15 | 15/15 | 15/15 |

1/16 网格上「不弹」的落差（覆盖块顶与黏液顶重合，落差从覆盖块顶量起，起点静止）：

| 覆盖 | 0.25–6.0 里不弹的落差 |
| --- | --- |
| 雪 1 层 (0.125) | 无（0.25–12 也无） |
| 雪 2 层 (0.25) | 1.125、1.5625、2.0625、2.6875、3.3125、4.0625、4.8125、5.6875 |
| 雪 3 层 (0.375) | 0.4375、0.6875、0.75、1.0、1.0625、1.125、1.4375、1.5、1.5625、1.9375、2.0、2.0625、2.5625、2.625、2.6875、3.1875、3.25、3.3125、3.9375、4.0、4.0625、4.6875、4.75、4.8125、5.5625、5.625、5.6875 |
| 雪 4 层以上 (≥0.5) | 全部 |

2 层的 8 个缝是预测后补测的（E3）：实测了 1.125 / 1.5625 / 2.0625 三处（都不弹）与 12 个
非缝落差（都弹），15/15。

两条前提：

1. 公式假设**从静止开始**（`v0 = 0`）。跳跃、被弹起后接手的高度带初速，等价于从更高处落，
   要按 `(preY, δy)` 重算，不能套落差表。
2. `0.2 / 0.5625 / 0.0784` 都是本版本的运行时常数；换版本要重新从 `docs/offsets` / roles 取。

## 7. 复现

**静态**：`idat` 打开 `%APPDATA%\levilauncher.exe\versions\<版本>\Minecraft.Windows.exe.i64`，
反编译 `0x148B5DB00`（判定）/ `0x141E144A0`（解析）/ `0x1431C2F50`（收集盒与填充）/
`0x1431DC500`、`0x1431DD080`（runner 与系统体）；或在 `.text` 里找 `movss` 引用
`0x14EA350B0`（0.080000117f）与 `addss` 引用 `−0.2f` 的站点。

**定位填充点**（本轮用的手法）：先 `hook_install` 解析器
（`mem_arg=0, mem_offset=-88, mem_size=128`）拿到 `MoveRequest` 的运行时地址，再
`watch_set(addr=MR+0x60, size=8, mode="w", thread="both")` 抓「谁在改表尾指针」；6 个写点里
`0x1431C35FA`（`add [r13+0x60], 0x18`）是 24 B 元素的 `push_back`，反编译它的宿主函数即得。

**动态**：3×3 黏液（`y=−60`）+ 石基座，`setblock ... snow_layer ["height"=N]`，
