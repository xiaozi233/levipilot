# 基岩版有 `16` 格/tick 的速度上限吗？（`1.26.51.01` 实测与机制解析）

在《我的世界》基岩版（MCBE）跑酷圈里，一直流传着一句话：**“玩家有 `16` 格/tick 的绝对速度上限。”** 现在可以给出明确结论：**这条上限真实存在，而且它的工作方式与多数人的直觉完全不同。**

理解基岩版的极限速度边界，需要记住三个最反直觉的事实：

1. **它不是“每轴各 `16`”，而是“三维总模长 ≤ `16`”**：`45°` 斜向冲刺撞顶时，单个水平轴最快只有约 `11.31` 格/tick，斜向总步长才是 `16`。
2. **它只拦“这一拍迈出几格”，不清空“体内攒下的动量”**：撞顶之后，只要你没有撞墙或落地重置对应轴，内部待执行位移依然能继续滚雪球突破 `16`（实测达 `19.8` 以上），冲出平台或松键降速后仍会按攒高的动量往外滑。
3. **满级迅捷和蓝冰都碰不到它**：`255` 级迅捷平地疾跑稳态只有 `14.65` 格/tick，而蓝冰滑度越高加速度反而越慢（稳态仅 `14.85`）；必须叠到**灵魂沙 + 灵魂疾行 III + 迅捷 255**，才能在游戏里亲眼看到角色稳稳停在 `16` 格/tick。

> **文档分工**：本文面向玩法理解、跑酷线路设计与 Java/Bedrock 机制对照，略去底层反编译地址与内部组件编号；完整函数定位、常量地址、全管线扫描与逐 tick 原始数据请参阅 [`notes/speed-limit-12651.md`](notes/speed-limit-12651.md)。
>
> **单位约定**：文中速度单位默认是 **格/tick**（$1\text{ 秒} = 20\text{ tick}$），括号内附 **格/秒** 方便直观对比。

## 三、`16` 格/tick 上限是怎么工作的？

### 1. 截断发生在一帧里的哪一步？

玩家每一帧推进位置的大致顺序如下：

```text
输入 / 疾跑 / 药水 ──▶ 写出“本拍打算走多远”（移动请求）
                             │
                             ▼
                  [抓取碰撞箱入口：检查模长]
                    ├─ ≤ 16 格：原封不动放行
                    └─ > 16 格：方向不变，整体缩放到 16 格
                             │
                             ▼
                  碰撞箱解算 ──▶ 写回最终玩家位置
```

只要本 tick 算出来的“移动请求”三维长度平方大于 $16^2 = 256$，游戏就会立刻把 $(v_x, v_y, v_z)$ 一起除以当前长度再乘以 `16`：

$$\sqrt{v_x^2 + v_y^2 + v_z^2} > 16 \implies \vec{v}_{\text{请求}}' = \vec{v}_{\text{请求}} \times \frac{16}{\sqrt{v_x^2 + v_y^2 + v_z^2}}$$

正因为它是按三维欧氏长度等比缩放，所以无论从哪几个方向叠加速度：

- **正对单轴直线冲刺**：理想上界是 `16.0` 格/tick；
- **45° 斜向冲刺**：两个水平轴各自只能分到 $16 / \sqrt{2} \approx \mathbf{11.3137}$ 格/tick（实测为 `(-11.31358, -0.07555, +11.31359)`）；
- **平地实测为什么从 `15.99982` 微升到 `15.99987`？** 这并不是单纯的浮点误差，而是角色站在地面时，每拍在碰撞前都会预设一个向下的重力微元 $v_y = -0.0784$。在落地碰撞把垂直位移清零之前，这个 `-0.0784` 先一起参与了三维模长缩放：
  - 第 3 拍水平请求 `16.60435`：$16 \times 16.60435 / \sqrt{16.60435^2 + 0.0784^2} = \mathbf{15.999821}$（实测 `15.99982`）；
  - 第 4 拍水平请求进一步涨到 `19.80618`：$16 \times 19.80618 / \sqrt{19.80618^2 + 0.0784^2} = \mathbf{15.999874}$（实测 `15.99987`）。

### 2. 为什么撞顶之后还能继续“攒超额动量”？

最关键的细节在于：**`16` 格/tick 的缩放只改写送进碰撞解算的“本拍请求位移”，在无碰撞的轴上，它既不覆盖角色“已完成位移”的历史记录，也不回写清空内部待执行位移（动量）。**

我们可以用一次实测直接验证这件事（灵魂沙 + 灵魂疾行 III + 迅捷 255 疾跑，每拍地面加速约 `10.7402`、地面摩擦 `0.546`）：

- 假如内部动量也一起被按死在 `16.0`，那么经历地面 `× 0.546` 摩擦之后，每拍末尾留在体内的待执行位移**无论如何不可能超过 $16.0 \times 0.546 = \mathbf{8.736}$**。
- 然而实测中，两拍连续撞顶时内部待执行位移依次涨到了 **`9.06598`（$= 16.60436 \times 0.546$）→ `10.81418`（$= 19.80619 \times 0.546$）**，双双显著越过 `8.736`！
- 在 `45°` 斜向测试里，第 3 拍正好冲出跑道悬空：当拍实际位移被压缩成 `(-11.31358, -0.07555, +11.31359)`，但垂直待执行位移依然是未缩水前的 **`-0.15523`**，水平内部动量也继续越过 `8.736`；结果飞到空中的第 4 拍，玩家在不受加速的空中直接走出了一步 **`9.09278` 格**。

也就是说：**只要没撞墙、没落回地面把对应轴清零，玩家就像在隐形跑道上不断往身体里继续“存速度”；步长被压死在每拍 `16` 格，但存起来的动量会在松手减速或飞出平台后照常兑现。**

## 四、为什么平时几乎撞不到 `16`？（常见速度源与蓝冰陷阱）

把基岩版各类高速移动方式放在同一张表里，就能一目了然：

| 移动方式 | 首拍或常见特征 | 稳态速度（格/tick） | 格/秒 | 会撞上 `16` 吗 |
| --- | --- | --- | --- | --- |
| **普通地面走路 / 疾跑** | 首拍 `0.098` / `0.1274` | `0.2159` / `0.2806` | `4.3` / `5.6` | 否 |
| **迅捷 255 普通地面走路** | 首拍 `5.1156` | `11.27` | `225` | 否 |
| **迅捷 255 普通地面疾跑** | 首拍 `6.6503` | `14.65` | `293` | 否（只差一点） |
| **蓝冰 + 迅捷 255 走路** | 首拍 `1.142` | 拟合 `11.42` | `228` | 否 |
| **蓝冰 + 迅捷 255 疾跑** | 首拍 `1.485` | 拟合 `14.85` | `297` | 否 |
| **灵魂沙 + 灵魂疾行 III + 迅捷 255** | 走路 4 拍撞顶 / 疾跑 2 拍撞顶 | **硬顶封在 `16.0`** | **`320`** | **是** |
| **创造模式飞行 / 疾跑飞行** | 滑行平稳 | `0.512` / `1.085` | `10.2` / `21.7` | 否 |
| **旁观者模式飞行** | 无碰撞穿墙 | `0.47`（标准水平） | `9.4` | 否（仍走移动管线） |
| **自由落体** | $v' = 0.98(v - 0.08)$ | 极限 **`-3.92`** | `-78.4` | 否 |
| **TNT `2.5` 格处爆炸** | 瞬间冲击 | 峰值 **`0.70`** | `14.0` | 否 |

这里有两个极容易让人看走眼的结论：

1. **满级迅捷本身摸不到 `16`**：哪怕叠到药水上限 `255` 级（移速属性 `5.22`），普通地面疾跑稳态也只有 `14.65` 格/tick。很多人测不出来上限、误以为“基岩版没有 `16` 限制”，就是卡在了这里。
2. **蓝冰加速反而慢得离谱**：蓝冰表面滑度（`0.989`）确实让松键后阻力高达 `0.90`，但基岩版每拍地面加速度会同步乘上一个滑度修正因子 $(0.6 / s)^3$。普通石头（$s = 0.6$）系数是 `1.0`，而蓝冰的系数只有 $(0.6 / 0.989)^3 \approx \mathbf{0.223}$！因此同为迅捷 `255`，蓝冰起步第一拍只有 `1.142` 格/tick（还不到普通地面 `5.12` 的四分之一），长距离跑满也不过 `14.85` 格/tick，永远摸不到 `16`。

### 亲手在游戏里触发一次 `16` 封顶

想亲眼验证 `16` 格/tick 上限，最简单稳定的方法是：

1. 铺一条长**灵魂沙**（或灵魂土）跑道；
2. 穿一双附魔了**灵魂疾行 III** 的靴子；
3. 开启**迅捷 255**（`/effect @s speed 400 255 true`）；
4. **直线疾跑**：速度会按 `10.74 → 15.99982 → 15.99987` 连续压顶在 `16`；改按 **走路** 也能在第 4 拍后顶到 `15.99983`；
5. **保持 `45°` 斜向前进**：两根水平轴各分摊约 `11.31` 格/tick，合成长度恰好等于 `16.0`。

> **关于绕过路径**：实测旁观者模式仍经过同一套移动系统，并非“无上限通道”；`/tp` 等传送命令则是直接覆盖坐标，完全不走移动速度管线，和速度上限不在同一条赛道上。至于鞘翅高空滑翔与载具乘客是否所有分支都经过这处截断，目前静态未发现第二处钳位，但尚未完成全场景实测验证。

## 五、容易与 `16` 上限混淆的另外三条边界

1. **自由落体终速 `-3.92` 格/tick**：
   这不是硬截断，而是重力减 `0.08` 再乘 `0.98` 空气阻力的自然极限：当 $0.98 \times (v - 0.08) = v$ 时，解得 $v = -3.92$（远不到 `16`）。实测从高空落下 `127` 拍时已加速到 `-3.6306`，与递推公式严丝合缝。
2. **极小速度归零（`1.19 × 10⁻⁷`）**：
   Java 版水平速度小到 `0.003`（部分版本）以下就会直接清零停住，但基岩版用的是单精度浮点最小有效差 `FLT_EPSILON`（约 `1.192 × 10⁻⁷`），实测滑行末尾能一路衰减到恰好 `1.1920928955078125e-07` 后下一拍归零。因此在基岩版停止移动后，角色会在微米级尺度多滑好几拍。
3. **联机时的“4 格拉回”阈值**：
   二进制里另一处容易被误认的常数 `16.0`，实际上是服务端“接受客户端位置的平方距离窗口”（$4^2 = 16$，即允许客户端与服务端位置相差 `4` 格以内）。它管的是联机防回弹校验，不是移动速度上限。
