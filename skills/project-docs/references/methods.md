# 文档写作与验收方法

## 1. 事实来源与冲突裁决

按以下顺序核对：

1. 当前代码、协议、配置、生成器和测试。
2. 当前有效的现场证据与原始日志。
3. 当前指南中的稳定契约。
4. 历史文档、提示词和候选报告。

逆向机制结论另按 `bedrock-re` 的证据等级处理：静态代码/常量支撑定案，动态观测用于对质和
证伪。不要用旧文档证明代码仍然如此，也不要用一次实测代替静态机制证明。

发现冲突时，先确认哪个事实为真，再改文档。无法确认时写“未核实/未定位”，列出验证入口，
不得选择更好看的旧结论。

## 2. 一篇文档的最小结构

按主题需要选择，不机械凑齐所有标题：

1. **用途与读者**：这篇文档解决什么问题。
2. **前提**：版本、权限、工具链、世界/配置要求。
3. **当前行为**：命令、步骤、字段、线程或生命周期。
4. **限制与失败语义**：超时、取消、旧代次、部分完成、未覆盖范围。
5. **验证与另见**：可复现命令、正主文档和证据链接。

规范文档写“必须/不要”；参考文档写字段和实际行为；指南给可执行步骤。不要在一篇文档里
同时扮演教程、完整协议、审阅报告和历史日志。

## 3. 写法

- 使用短段和明确主语，优先“谁在哪条线程做什么”，少用“目前/不断/彻底/完美/低成本”等
  没有证据的词。
- 命令、参数、字段、事件、路径和类型名使用反引号，保持代码中的大小写与下划线。
- 多行命令使用 fenced block；`py -3.11`、构建并发和必要环境变量不能省略。
- 表格只放真正并列的信息；步骤用编号列表，普通解释用正文。
- 当前事实直接写，不用日期作为“当前”的替代。日期只用于确有必要的版本/事件定位。
- 数值同时写清单位和语义，例如 tick、毫秒、字节、脚部/眼睛、接受/完成/效果。
- 链接到正主文档的对应小节；不要复制整段后只改几个数字。

## 4. API、协议与生命周期

- 参数默认值、可选性、权限、错误 reason 和字段名称必须与实现一致。
- 区分 queued/accepted、后台完成和游戏实际效果；需要回读才能确认的效果必须写明。
- 异步操作写清忙、截止、取消、退出、重连、旧代次和部分副作用。不能暗示超时可抢占已开始
  的 SDK 调用或自动回滚。
- 协议新增字段不能写成旧字段已删除；未知命令和版本降级行为保持可查。
- 容量、预算和分配位置属于实现契约时不能为了精简而删除。

## 5. 验收记录

每条有效结果至少能回答：运行了什么、覆盖什么、结果是什么、还有什么没证明。

- 离线/native、基础现场、完整现场分别记录，不能互相替代。
- 通过数包含分母；skip 单独列出，required skip 在严格模式中是失败。
- “当前基线”只能来自当前代码的实际执行；后续变更后按影响范围重验或明确旧基线。
- 未执行的检查写“未运行”，不要写“预计通过”。首轮失败和修正后的结果都可简述，但不在
  当前文档堆叠每轮详细过程。
- 性能结论需要受控对照；native 零分配/并发模型不能证明游戏内时序收益。

当前验收放 `docs/reliability-repairs.md`，实现语义放 `docs/mod-internals.md`，不要在多个
文件复制完整验收表。

## 6. 精简与删除

先删除重复、已被推翻且无需保留的过程内容，再压缩句子和结构。不能删除：

- 执行所需前提、权限、坐标/单位、关键常量和错误语义。
- 当前未决问题、外部限制和未验收范围。
- 静态守卫或公开契约依赖的事实。
- 逆向证据、原始 probe、撤回关系和版本角色。

过程性提示词、交接稿、候选报告和痛点清单优先放 `out/`，不要随 Git 增长。删除受 Git 管理
的文件前搜索其文件名与相对链接，更新索引；不要留下“详见某文件”的空引用。

## 7. 逆向公开结论

原始证据可以继续按调查轮次保留，但公开正文必须区分当前结论、历史现象和撤回项。删除过时
提示词不等于删除证据；保留函数、数据结构、 probe 和复核路径。个人路径、用户名和私有运行
信息必须脱敏。

## 8. 维护本 skill

文档类型、正主位置、检查命令或项目契约改变时，同步更新本 skill 与索引。不要另建一份
“文档规范 v2”或按日期追加补丁章节。
